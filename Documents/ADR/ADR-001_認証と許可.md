# ADR-001 認証と許可（SERVICE-PLATFORM）

| 項目 | 内容 |
| --- | --- |
| ステータス | 採用（Accepted） |
| 影響範囲 | 認証、利用者管理、機器割当、サービス許可、通知、監査 |

この ADR は採用した設計と技術的な根拠を記録する。公開ツリーには基盤の参考実装と独立した PoC を含む。設計の採用と全機能の実装完了は別であり、特定の稼働環境の構成や対応状況を説明するものではない。

## 背景

顧客単位・利用者単位で操作を追跡し、利用に応じた請求の根拠にできる独立した認証が必要である。新しい基盤ではパスワードに頼らず、パスキーを標準にする。招待、紛失・侵害からの回復、管理操作、機器の利用主体の変更までを共通の認可モデルで扱う。

## 決定事項

```text
サインイン（パスキー優先）
  ├─ 機器単位 → 割当確認・機器ログイン → 許可されたサービス
  └─ アカウント単位 → パスキーの管理・割当と許可の一覧・管理機能

API → JWT 検証 → sub / user_id の対応 → 利用者の有効状態
    → 利用期間・割当・ログイン記録・サービス許可
    → 管理操作の追加検証 → 処理 → user_id による監査
```

### D1. 専用のユーザープール、サインインの方式、トークン

- 認証は専用の Cognito ユーザープール。他システムのプールを借りない。
- パスキーを優先する。
- お客様はパスワード無しで作成し、初回と回復はメールのコード (EMAIL_OTP)、常用はパスキー。admin はパスワード + TOTP。
- トークンは ID / アクセス 60 分、更新 24 時間、保存場所は localStorage。
- 1 人の利用者がパスキーを複数登録できる (PC に 1 個、スマホに 1 個など。複数登録の方針)。

- 機能プランは Essentials (`UserPoolTier: ESSENTIALS`)。パスキーは Lite では使えない。Plus は使わない。
- サインインは choice-based (USER_AUTH)。アプリクライアントの ExplicitAuthFlows は `ALLOW_USER_AUTH`。`ALLOW_REFRESH_TOKEN_AUTH` は外す。`ALLOW_USER_SRP_AUTH` は、admin の SRP サインインを使う構成では残す。`ALLOW_USER_AUTH` がパスワードと SRP を含むので、残しても攻撃の入口はほとんど増えない (推論)。
- 画面はパスキー (`WEB_AUTHN`) を第一候補として求める (Amplify の `signIn` に `authFlowType: 'USER_AUTH'`、`preferredChallenge: 'WEB_AUTHN'`)。パスキーを持たない利用者には Cognito が候補の一覧 (SELECT_CHALLENGE) を返すので、画面は候補から選ばせる。
- パスキーの前にユーザー名 (メールアドレス) が要る。入力欄の自動補完 (autofill) では始められない (推論)。前回のメールアドレスをブラウザに覚えておく。
- サインインの要素 (`SignInPolicy.AllowedFirstAuthFactors`) は `PASSWORD`・`WEB_AUTHN`・`EMAIL_OTP` (下の案 B)。`PASSWORD` は外せない。`WEB_AUTHN` だけにもできない。
- パスキーの設定: RP ID は D7。利用者の確認 (`WebAuthnUserVerification`) は `required` (指紋・PIN などの本人確認を伴う認証器だけ)。`WebAuthnFactorConfiguration` は既定の `SINGLE_FACTOR`。
- MFA はプールで任意 (`MfaConfiguration: OPTIONAL`、TOTP だけ)。TOTP を持つのは admin だけにする (D9)。必須 (ON) にしないのは、必須にするとメールのコードが使えず、パスキーも passkey MFA を有効にしたときしか使えないため。
- パスキーはサインイン後にだけ登録できる。招待した利用者には managed login も登録を促さないので、初回サインインの直後に画面から登録を促す。1 人で複数持てる (下の「パスキーの複数登録」)。

- 更新トークンの rotation を採る。`RefreshTokenRotation` は `Feature: ENABLED`、`RetryGracePeriodSeconds: 30`。
- お客様のパスワードの後付けは、ユーザープールの web ACL で ChangePassword を Block して止める。下の「パスワードの後付け」。

パスキーの複数登録:
- 1 人の利用者 (独自の user_id、Cognito の 1 利用者) が、パスキーを複数登録できる。PC に 1 個、スマホに 1 個のように、端末ごとに登録する使い方を想定する。
- 上限は 1 利用者あたり 20 個 (Cognito の制限で、変えられない。参考資料)。上限に達したら、使わなくなったものを消してから足す。
- アカウントの画面の「パスキーの管理」(D5) で、本人が次を行う。
  - 一覧: 登録済みのパスキーごとに、名前・登録日・認証器の種類を出す。Amplify の `listWebAuthnCredentials` (Cognito の ListWebAuthnCredentials) が `friendlyCredentialName`・`createdAt`・`authenticatorAttachment` を返す (PoC は Amplify 6.20 を使用)。認証器の種類は `platform` (端末に組み込みの認証器。内蔵の指紋センサーなど) か `cross-platform` (端末とは別の機器。Bluetooth のセキュリティキーなど)。Cognito はこの項目を返さないことがある (必須の項目でない) ので、無ければ空欄にする。
  - 追加: `associateWebAuthnCredential` (サインイン済みのときだけ使える)。端末を設けるときは、その端末でサインインして (メールのコードなど) から登録する。同じ認証器に 2 つ目は作れない (Cognito が登録済みの一覧 `excludeCredentials` を渡し、ブラウザが断る。PoC 12)。
  - 削除: `deleteWebAuthnCredential` で 1 件ずつ消す。消せるのは本人だけ (D8)。
- 名前: Cognito が登録のときに自動で付ける (`FriendlyCredentialName`。公式の説明は「自動で生成した名前」)。登録の API (CompleteWebAuthnRegistration) の要求はアクセストークンと認証器の応答だけで、名前を渡す項目は無い。Amplify の `associateWebAuthnCredential` も引数を取らない。付け替える API も無い (WebAuthn の API は登録の開始・完了、一覧、削除の 4 つ)。自動の名前は端末の名前ではなく、種類の名前 (Device-bound Passkey / Roaming passkey) だった (PoC 12)。画面は種類の名前と登録日時を出す。利用者が付ける名前を表示する場合は、credentialId ごとの台帳で管理する。
- 推奨する運用: 端末ごとに 1 個 (PC とスマホ) を登録しておく。1 台を失くしても、もう 1 台で入れる (締め出されにくい)。失くした端末のパスキーは、もう 1 台から消せる (D8 手順 1)。盗難が疑われるときは D8 手順 2 による。どの端末も使えないときの回復は、メールのコードで行う。
- admin は TOTP を設定するので、パスキーでサインインできない (D9)。この節は主にお客様と、admin でない社員に当たる。

招待と回復の 2 案 (案 B を採用):

| 観点 | 案 A: 一時パスワードで招待 | 案 B: パスワード無しで招待 (採用) |
| --- | --- | --- |
| 招待 | AdminCreateUser。一時パスワードをメールで送る | AdminCreateUser で一時パスワードを省く。招待メールに一時パスワードを入れない |
| 初回 | 一時パスワード → 本パスワードを決める → パスキーを登録 | メールのコード (EMAIL_OTP) でサインイン → パスキーを登録 |
| 常用 | パスキー。パスワード欄は画面に出さない | パスキー |
| パスキーを失くしたとき | パスワードでサインイン → 登録し直す | メールのコードでサインイン → 登録し直す |
| パスワード | 残る。後から消せない。画面で隠しても、API を直接呼べばパスワードでサインインできる | 作成のときは持たない。本人が後から足す入口は Cognito の設定では止められないので、web ACL で止める (下の「パスワードの後付け」、WAF の方針) |
| 受信箱への依存 | パスワードの再設定をメールで行うなら、受信箱が回復の要になる | 受信箱が回復の要になる (メールを取られると乗っ取られる) |
| 前提 | USER_AUTH 経由で一時パスワードの変更 (NEW_PASSWORD_REQUIRED) に進む (PoC 4) | EMAIL_OTP は Essentials と SES 送信 (`EmailSendingAccount: DEVELOPER`) が要る。MFA を設定した利用者はメールのコードを使えない |

- 案 B を採った理由: (1) パスワードは一度持たせると消せない。案 A から案 B へ移るには利用者を作り直すことになる。逆に案 B の利用者には後からパスワードを足せる (AdminSetUserPassword、推論)。(2) 案 A では全員がパスワードを持ち、「パスワードは招待と回復だけ」を Cognito では強制できず、画面で隠すだけになる。案 B では、本人が自分で足さない限りパスワードを持たない。(3) SERVICE-PLATFORM がパスワードを持たせるのは admin だけになり (パスワード + TOTP)、パスワードを持つ役割を限定できる (D9)。
- 補足 (採った根拠には使わない): Plus を使わない (D1) ので、パスワードへの総当たりは WAF のレート制限で受けることになり、パスワードを持つ人が少ないほど守る範囲は狭い。なお Plus の漏えいパスワードの照合は、SRP を対象外と明記している (確認済)。USER_AUTH を対象とする記載は無く、評価されるかは未確認。
- 案 B でも、サービス提供者の admin は一時パスワードで招待し、パスワード + TOTP でサインインする (D9)。プールは PASSWORD を常に持つので、パスワード有りと無しの利用者を混ぜられる。
- 回復の設定 (`AccountRecoverySetting`) は `admin_only`。パスワード無しの利用者の「パスワードを忘れた」(ForgotPassword) は、この設定で止まる (PoC 3)。admin のパスワードの回復は、別の admin が一時パスワードを設定して渡す (AdminSetUserPassword、`Permanent=false`)。`admin_only` が止めるのは「パスワードを忘れた」からの回復で、サインイン済みの本人がパスワードを設けること (下) は止めない。

パスワードの後付け (お客様):
- 事実: ChangePassword は本人のアクセストークンで呼ぶ公開 API で、IAM では絞れない。パスワードを持たない利用者は、前のパスワード (`PreviousPassword`) を省いて新しいパスワードを設定できる (公式)。`PASSWORD` はサインインの要素から外せない (参考資料)。
- このため、「作成のときはパスワードを持たない」 は保てるが、「その後もパスワードの入口が無い」とは言えない。SDK を直接呼べば、サインインできる本人 (または本人のセッションを得た者) はパスワードを足せ、足した後は `PASSWORD` でもサインインできる (PoC 14。Amplify の `updatePassword` は旧パスワードを求めて手前で止めるだけ)。これを Cognito の設定だけで防ぐ手段は無い。
- 方針:
  - SERVICE-PLATFORM の画面には、お客様向けのパスワードの設定・変更と、パスワードでのサインインを出さない。
  - 塞ぐ: ユーザープールの web ACL で、`x-amz-target` が `AWSCognitoIdentityProviderService.ChangePassword` の要求を Block する。dev と本番の両方に、最初から Block で置く (D9 のレート制限の「最初は Count」は、このルールには当てはめない)。PoC 14 で 403 になり、ほかの公開 API、パスキーのサインイン、admin の招待 (一時パスワード → 本パスワード)、TOTP の登録、AdminSetUserPassword は止まらなかった。
  - admin 自身のパスワードの変更: ChangePassword を使わない。別の admin が AdminSetUserPassword (`Permanent=false`) で一時パスワードを出し、本人が NEW_PASSWORD_REQUIRED で決め直す。
  - 見つける手段: admin は AdminGetUserAuthFactors の `ConfiguredUserAuthFactors` で、利用者が `PASSWORD` を使えるかを見られる (公式)。後付けした利用者に `PASSWORD` が出ることを PoC 14 で確かめた。admin-users の利用者の画面に出す。
- 残る危険: web ACL が外れると、本人 (または本人のセッションを得た者) がパスワードという弱い入口を足せる。足しても SERVICE-PLATFORM の API を通らないので監査テーブルには残らず、アカウントの CloudTrail に sub 付きで残る (D12、PoC 13)。WAF で止めた要求は、PoC の検索の時点と時間窓では CloudTrail に検出しなかった (PoC 13)。止めた記録は WAF のログで見る。セッションを奪った者が足した場合、D8 手順 3 (全セッションの失効だけ) では足されたパスワードが残る。乗っ取りの疑いでは、利用者ごと消す D8 手順 2 か 4 を使う。

トークンの有効期間と保存場所の比較 (T2 を採った。トークンの方針):

| 案 | ID / アクセス | 更新の期限 | 保存場所 | 利便 | API を呼べる最長の時間と保存データ |
| --- | --- | --- | --- | --- | --- |
| T1 | 60 分 | 30 日 | localStorage | サインイン頻度が低い | サインインから 30 日 + 60 分。保存データはサインアウトまで残る |
| T2 (採用) | 60 分 | 24 時間 | localStorage | 1 日に 1 回のサインイン。新しいタブや /camera/ の別ビルドでも同じセッション | サインインから 24 時間 + 60 分。保存データはサインアウトまで残る |
| T3 | 60 分 | 12 時間 | sessionStorage | タブを閉じるたび、新しいタブ (通知メールのリンクなど) を開くたびにサインイン | タブを開いたままなら 12 時間 + 60 分。タブを閉じると保存データが消える |

- 期限の読み方: 更新トークンの期限は最初のサインインから数え、更新しても延びない。更新で得られるのは新しい ID / アクセストークン (60 分) で、期限の直前に更新すると、そのトークンがさらに 60 分使える。localStorage の保存データは期限が過ぎても自動では消えず、サインアウト (Amplify の `signOut`) で消える。共用の端末では、使い終えたらサインアウトする (画面にサインアウトを常に出し、案内にも書く)。
- XSS の残余リスク: localStorage も sessionStorage も同じ origin のスクリプトから読める。XSS が成立すれば、どちらに置いても更新トークンを含むトークンを読まれ、更新の期限まで使われうる。CSP は XSS を起こしにくくする軽減策で、保証ではない。読まれた後の被害は、更新の期限、台帳の停止 (D3)、AdminUserGlobalSignOut (更新トークンの失効) で区切る。
- 更新トークンを使うたびに新しいものへ替える rotation を採る (AWS の推奨。rotation の方針)。Amplify 6.20 は `GetTokensFromRefreshToken` で更新し、古い更新トークンの再利用は `RefreshTokenReuseException` になる (PoC 10)。`REFRESH_TOKEN_AUTH` とは併用できないので、ExplicitAuthFlows から `ALLOW_REFRESH_TOKEN_AUTH` を外す。猶予 (`RetryGracePeriodSeconds`) は 30 秒にし、複数のタブと /camera/ の同時の更新を許す。rotation でも期限は最初のサインインから延びず、`auth_time` も変わらない (PoC 10)。
- Amplify v6 で sessionStorage にする方法は `cognitoUserPoolsTokenProvider.setKeyValueStorage(sessionStorage)` (Amplify 公式)。

理由:

- パスキーは Essentials 以上と USER_AUTH でしか使えない (参考資料)。
- Plus の threat protection は、対象フローに USER_AUTH の記載が無く、評価されるかは未確認。レート制限はしない。Adaptive authentication の MFA はパスキー優先と相性が悪い (参考資料)。

影響:

- 構成要件: infra/core の UserPool と UserPoolClient を構成する (階層、SignInPolicy、WebAuthn の 3 項目、ExplicitAuthFlows、AccountRecoverySetting、トークンの期間、rotation、web ACL)。`auth.ts` に USER_AUTH の分岐 (パスキー、メールのコード、候補の選択) とパスキーの登録・一覧・削除 (1 人で複数。一覧に名前・登録日・認証器の種類) を設ける (Amplify 6.10.0 以降。土台は 6.20)。
- 利用者: 初回はメールのコードでサインインし、続けてパスキーを登録する。端末ごと (PC とスマホなど) にパスキーを足せる。端末を替えたら、新しい端末でサインインし直して (メールのコードなど) 登録し、古いものを消す。

構成要件: UserPoolTier は ESSENTIALS、USER_AUTH、WEB_AUTHN / EMAIL_OTP / PASSWORD、WebAuthn の UV は required。一般利用者のパスワード後付けは WAF で ChangePassword を Block する。管理者のパスワード変更は別の admin が AdminSetUserPassword（Permanent=false）を実行し、本人が NEW_PASSWORD_REQUIRED で確定する。招待とメールコードの文面は利用者が理解できる言語にする。

### D2. 招待制と email 属性の守り

- 自己登録は作らない。招待制だけにする。

- `AdminCreateUserConfig.AllowAdminCreateUserOnly: true` で、プールが自己登録 (SignUp) を受け付けない。
- 招待では AdminCreateUser に `email` と `email_verified=true` を渡す。メールの宛先は admin が入力し、admin でない利用者 (お客様と社員) は届いたメールのコード (EMAIL_OTP) でサインインして受信を示す。EMAIL_OTP のサインインに成功すると `email_verified` が true になる。admin には招待メールを送らず、一時パスワードを別経路で渡す (D9)。
- email は利用者が書き換えられないようにする。
  - UserPoolClient の WriteAttributes を明示し、`email` と `email_verified` を入れない。明示しないと全ての標準属性が書ける。
  - `UserAttributeUpdateSettings.AttributesRequireVerificationBeforeUpdate: [email]`。万一 email が更新されても、検証されるまで旧い値が有効のまま残る。
  - WriteAttributes に入れなければ、利用者は `email_verified` も `email` も書けない (PoC 2)。
- email を変えるのは admin だけ (AdminUpdateUserAttributes で `email` と `email_verified=true`)。変えたことは監査に残す (D12)。

理由:

- 招待した識別情報の完全性を保ち、email 属性の本人による書換えを禁止する。

影響:

- 構成要件: core テンプレートの Schema、AdminCreateUserConfig、UserAttributeUpdateSettings、PreSignUp の関数、UserPoolClient の WriteAttributes を設定する。テンプレートのテストを設ける。
- 運用: 社員も admin が招待する。メールアドレスの変更は admin への依頼になる。
- 利用者: 自分でメールアドレスを変える画面は無い。

構成要件: AllowAdminCreateUserOnly=true。PreSignUp は PreSignUp_SignUp を拒否し、AdminCreateUser による招待を通す。email はスキーマで必須にせず、WriteAttributes は name など必要な属性だけに限定し、email と email_verified を含めない。AttributesRequireVerificationBeforeUpdate に email を指定する（PoC 1・2）。

### D3. 利用者の識別子 (独自 user_id)

- 利用者の識別子は独自の user_id を挟み、認証方式に依存させない。

- user_id は ULID (利用期間 period_id と同じ形式)。招待のときに台帳で採番する。
- 台帳に「利用者」の行 (user_id ごと) と「sub の引き当て」の行 (sub → user_id) を持つ。API は検証済みのトークンの sub から user_id を GetItem で引く (強い整合の読み取り)。
- 再招待 (AdminDeleteUser → AdminCreateUser) で sub が変わっても、新しい sub を同じ user_id に結び直す。古い sub の行は消さず、無効の印を付けて残す。CloudTrail の `additionalEventData.sub` から後で user_id を引くためである。API の引き当ては、無効の印の付いた行を「引けない」として扱う (403)。
- 業務データ（割当、ログイン記録、監査、サービス設定の操作者）はすべて user_id で保持する。
- 台帳の利用者に「状態」(有効 / 停止) を持ち、全ての API が毎回確かめる。停止中でも呼べる API は、D9 の「停止中でも呼べる API」の 2 つだけ。Cognito の無効化と合わせて使うと、発行済みのトークンが期限内でも即時に止まる。
- Cognito のカスタム属性に user_id を入れる案は採らない。カスタム属性は追加すると消せず、引き当ては台帳で足りる。

理由:

- 参考資料、admin が他人のパスキーを消す API は無い。紛失・乗っ取りへの代わりの手段は「削除して再招待」で、そのとき sub が変わる。sub を業務データの鍵にすると、再招待のたびに付け替えが要る。

影響:

- 構成要件: 台帳 (D4) と shared レイヤの認証 (`auth.py`) に「sub → user_id と状態の確認」を設ける。admin-users の識別子を sub から user_id に替える。
- 運用: 再招待は admin-users の操作 1 つにまとめる (削除、作成、引き当ての付け替えと古い sub の行の無効の印、admin グループの付け直し。admin なら admin の状態を「準備中」に戻す。台帳は有効に戻すまで停止のまま。D8)。
- 利用者: 再招待されても、通信機の割り当てと履歴は残る。

### D4. 役割と許可のモデル

- 許可はサービス提供者の admin が管理する。利用者を機器の利用期間に割り当て、サービスの許可も同じ期間に結び付ける。
- 機器の利用期間は組織・開始・終了を持つ。1 台で稼働中の期間は 1 つだけとし、条件付き書込みで守る。
- 割当ごとに assignment_id（ULID）と valid_from / valid_to を持つ。再割当では新しい ID を発行し、以前の行を上書きしない。
- 認可はすべて API 側で行う。次の条件をすべて満たすときだけ処理する。
  1. 機器に稼働中の利用期間 P がある。
  2. 利用者の割当が P に属し、有効期間内である。
  3. ログイン記録が同じ assignment_id に属し、割当開始以後かつ 12 時間以内である。
  4. サービスの許可が P に属し、有効期間内である。
- 機器の利用主体を変えるときは、期間終了・割当終了・許可終了・ログイン記録削除・機器認証情報の更新を一体で扱う。新しい利用者には新しい期間と割当を作る。
- サービス固有のデータも P に結び付け、利用者が参照できる履歴を割当の有効期間内に限定する。保持・削除の条件はサービスごとに定義する。

許可の単位の比較:

| 案 | 評価 |
| --- | --- |
| サービス × 機器の利用期間（採用） | 利用主体の変更で割当・許可・ログイン記録をまとめて無効にでき、請求の根拠となる期間も記録できる |
| サービス × 利用者 | 単純だが、機器の利用主体の変更を表現できない |
| サービス固有のデータ単位 | 個別サービスには適するが、共通のサービス一覧と機器の管理に使いにくい |

台帳は core の DynamoDB テーブルに置き、名前を SSM で公開する。admin-users と機器ログイン API が書き、各サービスは shared レイヤ経由で読む。

| データ | PK | SK | 主な項目 |
| --- | --- | --- | --- |
| 利用者 | `USER#{user_id}` | `PROFILE` | sub、email、状態、組織、別経路の連絡先、admin の状態、mfa_enabled_at、作成者、日時 |
| sub の対応 | `SUB#{sub}` | `USER` | user_id、無効の印 |
| 利用期間 | `DEVICE#{account}` | `DPERIOD#{device_period_id}` | 組織、開始・終了、状態。稼働中の期間は同じ PK の CURRENT で指す |
| 割当 | `DPERIOD#{device_period_id}` | `USER#{user_id}#{assignment_id}` | valid_from / valid_to、役割、機器識別情報、割当者 |
| 割当の逆引き | `USER#{user_id}` | `ASSIGN#{device_period_id}#{assignment_id}` | 機器アカウント、有効期間（または GSI） |
| 許可 | `DPERIOD#{device_period_id}` | `GRANT#{service}#{grant_id}` | 開始・終了、状態、許可者 |
| ログイン記録 | `USER#{user_id}` | `LOGIN#{account}` | assignment_id、device_period_id、ログイン時刻、期限 |
| 認証失敗回数 | `DEVICE#{account}` | `PINFAIL` | 回数、集計開始、制限終了時刻 |

admin が「招待 → 利用期間の開始 → 割当 → 許可」を管理する。割当を終えるときは履歴を残し、ログイン記録を削除する。削除が遅れても、認可条件 2 と 3 により以前の記録を拒否する。

### D5. 入り方の選択と機器ログイン

- サインイン後は「機器単位」と「アカウント単位」を選ぶ。機器単位では、割当確認と機器認証を経て許可されたサービスの一覧へ進む。
- 機器認証は、機器の識別情報と暗証番号を外部の検証インターフェースで照合する。外部データ源と接続先は環境ごとに設定し、検証にはテスト用データを使う。
- 照合前に利用期間と割当の有効性を確認する。成功したら assignment_id に結び付いた 12 時間のログイン記録を作る。
- DynamoDB TTL による削除の時刻に依存せず、API は毎回期限を確認する。
- 暗証番号は保存せず、ログ・監査・エラー応答にも出さない。ブラウザはメモリにだけ保持し、照合後に破棄する。
- 連続失敗を機器単位で制限し、WAF のレート制限と重ねる。初期設定例は 10 分に 5 回失敗で 10 分停止（429）。実際の閾値は負荷試験で決める。
- アカウント画面には複数パスキーの一覧・追加・削除、自分の割当と許可を表示する。admin には招待・停止・再招待、期間・割当・許可の管理、TOTP 登録を提供する。

機器の認証とサービスの認可を分離することで、各サービスは共通の台帳に基づいて処理を許可できる。

### D6. 最初に載せるサービスの SPA の配置

- 最初に載せるサービス（このリポジトリには含めない）は、独立したビルドとして同一 origin のサブパスに配置する。PoC のパスは `/camera/`。
- 同じ Cognito プール・アプリクライアントと Amplify 設定を使い、localStorage のセッションを共有する。別バンドルを新しいタブから開いてもセッションを取得できた（PoC 7）。
- CloudFront のサブパス用 behavior、S3 の接頭辞、SPA フォールバック、CSP を含む応答ヘッダを定義する。ルート SPA とサブパスの index.html をそれぞれ返す。
- 起動時に機器の識別子を渡す場合も、API は台帳で利用期間・割当・ログイン記録・許可を再確認する。

独立したビルドを採る理由は、サービスの UI と共通基盤を別々に更新できるため。同一 origin のスクリプトが同じ保存領域を読めるため、配信するすべてのバンドルを同じ信頼境界として管理する。

### D7. パスキーの RP ID

- ドメインは service-platform.example-cloud.com (dev は service-platform-dev.example-cloud.com)。RP ID がここに固定されるので後から変えない。
- RP ID は各環境のドメイン名そのもの。親ドメインにしない。dev と本番でパスキーは別。

- RP ID は、本番は service-platform.example-cloud.com、dev は service-platform-dev.example-cloud.com (各環境のサイトの FQDN)。親ドメイン example-cloud.com にはしない。
- dev と本番でパスキーは共有できない。プールが別なので、同じ RP ID にしても dev で登録したパスキーは本番の利用者に結び付いていない (推論、確度は高い)。利用者は環境ごとに登録する。
- ローカル開発 (localhost) では、RP ID が localhost でないとブラウザが拒む (推論)。ローカルの独立した PoC では RP ID を localhost にする。

理由:

- WebAuthn の仕様では、子ドメインから親ドメインの RP ID を使える。しかし Cognito が子ドメインの origin を受け付けるかは公式文書で確かめられない (未確認)。
- 親ドメインにすると、example-cloud.com 配下の別のサイト で動くスクリプトが、SERVICE-PLATFORM の RP ID のパスキーで認証器を呼び出せる (仕様 §13.4.8)。Cognito がそのサブドメインの origin からの応答を有効な認証として受け付けるなら (未確認)、そのページから SERVICE-PLATFORM にサインインできてしまう。受け付けないなら、親ドメインの RP ID では service-platform.example-cloud.com からの登録・認証そのものが通らないおそれがある (参考資料)。
- 共有の利点 (dev と本番で同じパスキー) はプールが別なので得られない。
- RP ID を変えると全員が登録し直しになる。公開前に決める。

影響:

- 構成要件: core テンプレートの `WebAuthnRelyingPartyID` を環境のドメインにする (63 文字以内に収まる)。
- 運用: dev で試す社員は dev 用にもパスキーを登録する。
- 利用者: 影響なし (本番だけを使う)。

### D8. admin が利用者のパスキーを消す手段

- admin が他人のパスキーを消す API は無いので、本人が消す。盗難のときは、無効化 → 全セッション失効 → 削除 → 再招待とし、user_id は保つ。

- admin が他人のパスキーを一覧・削除する API は無い (参考資料)。admin に分かるのは、パスキーを 1 つ以上持つか (AdminGetUserAuthFactors の WEB_AUTHN) まで。
- 代わりの手順を 4 つ用意する。普段は手順 1 と 2 を使い、手順 3 は一時的な措置、手順 4 は受信箱の乗っ取りの疑いのときに使う。

| 手順 | 場面 | 操作 | 結果と注意 |
| --- | --- | --- | --- |
| 1 本人が消す | 端末を替えた、古いパスキーを整理したい | 本人がアカウントの画面で一覧 → 削除 (`deleteWebAuthnCredential`) | 正規の方法。本人がサインインできること (別の端末のパスキー、またはメールのコード)。端末ごとに登録していれば、残った端末で入って消せる (D1 の「パスキーの複数登録」) |
| 2 無効化 → 再招待 | パスキーの盗難・乗っ取りの疑い、本人がサインインできない、admin が TOTP を失くした  | admin が台帳で停止 → AdminDisableUser → AdminUserGlobalSignOut → AdminDeleteUser → AdminCreateUser で再招待 → 新しい sub を同じ user_id に結ぶ → 下の「再招待の後の復帰」を経て台帳を有効に戻す | パスキーも、後から足されたパスワード (D1) も消える (PoC 8)。user_id・割り当て・履歴は残る。有効に戻すまで台帳は停止のまま (呼べるのは D9 の例外の API だけ)。復帰の条件は admin とそれ以外で違う (下の表) |
| 3 全セッションの失効だけ | 端末を一時的に失くした (見つかる見込みがある) | admin が台帳で停止 → AdminUserGlobalSignOut | パスキーと、後から足されたパスワード (D1) は残る。再び使えるようにすると、同じパスキーがまた使える。見つからなければ手順 2 へ |
| 4 受信箱の乗っ取りの疑い | お客様のメールが他人に読まれている (メールのコードで入れるので、他人がサインインし、その人のパスキーを足せる) | 下の「受信箱が侵害されたときの回復」 | 同じメールアドレスへそのまま再招待しない (攻撃者もメールのコードで入り直せる) |

- 無効化 (AdminDisableUser) だけではパスキーは消えない (推論)。再び有効にすると同じパスキーが使えるので、盗難のときは必ず削除して再招待する。
- AdminUserGlobalSignOut の後も、発行済みのトークンは期限まで JWT authorizer を通る (推論)。台帳の停止を全 API が確かめるので、SERVICE-PLATFORM の API はすぐ止まる (D3。例外は D9 の「停止中でも呼べる API」の 2 つだけ)。
- パスキーの追加・削除とパスワードの後付けは、画面 (Amplify) が Cognito を直接呼ぶので SERVICE-PLATFORM の監査テーブルに残らない (D12)。盗難や乗っ取りを調べるとき、監査テーブルだけでは「いつ誰のパスキーが足されたか」は分からないので、アカウントの CloudTrail を sub で引く (D12、PoC 13)。admin の画面で分かるのは、パスキーを 1 つ以上持つか (と、`PASSWORD` を使えるか) までである。乗っ取りの間に足されたものは、手順 2 / 4 の削除で消える (PoC 8)。
- admin の回復で「TOTP の解除だけ」は使わず、手順 2 にする。TOTP を外すと、TOTP の間に登録したパスキーとメールのコードで入れるようになる (PoC 11)。TOTP の現在状態は AdminGetUser の UserMFASettingList で見る。AdminGetUserAuthFactors の `ConfiguredUserAuthFactors` は、TOTP を外しても `SOFTWARE_TOKEN` を残し、使えない要素も出す (PoC 5 / 11)。

再招待の後の復帰 (手順 2 と手順 4 で共通。利用者の種別で分ける):
- 順序は 停止 → 再招待 → 本人の登録 → 別経路の確認 → 有効。台帳は再招待の後も「停止」のままで、有効に戻すまで SERVICE-PLATFORM の API は 403 になる。例外は D9 の「停止中でも呼べる API」の 2 つ (admin の「TOTP の登録を終えた」API と、自分の状態を読む API) だけ。
- admin でない利用者は、2 と 3 の順を問わない (手順 4 では 3 を再招待より前に行う)。admin は 2 の後に 3 を行う (登録の時刻を確かめるため)。

| 段 | admin でない利用者 (お客様・社員) | admin |
| --- | --- | --- |
| 1 停止と再招待 | 手順 2 (手順 4 なら下の 1〜5)。招待はパスワード無し (メールのコード) | 手順 2 と同じく停止 → 削除 → 作成。作成は admin の招待と同じく、招待メールを送らず (`MessageAction=SUPPRESS`)、一時パスワードを別経路で渡す。admin グループに付け直し、台帳の `mfa_enabled_at` を消し、admin の状態を「準備中」に戻す (前の「有効」は引き継がない) |
| 2 本人の登録 | 本人が新しい招待のメールのコードでサインインし、新しい端末でパスキーを登録する。画面が Cognito を直接呼ぶので、SERVICE-PLATFORM の API は通らない | 本人が一時パスワードでサインインし、本パスワードを決め、TOTP を登録して「TOTP の登録を終えた」API を呼ぶ (D9 の例外 1)。admin の状態は「確認待ち」になる。パスキーの登録は求めない (admin はパスワード + TOTP で入り、パスキーでは入らない。D9) |
| 3 別経路の確認 | admin が、招待のときに台帳に控えた連絡先 (組織の窓口の電話など) で、本人と組織の窓口に確かめる。メールでの申し出だけでは戻さない。パスキーの登録は AdminGetUserAuthFactors の `WEB_AUTHN` で確かめる | 本人以外の admin (使える admin がいなければ IAM の権限を持つ運用者が scripts で) が、別経路で本人を確かめ、登録の時刻 (`mfa_enabled_at`) が本人の操作と合うことを確かめる |
| 4 有効に戻す | admin が台帳を「有効」に戻す。手順 4 では、受信箱の安全確認 (または宛先の変更) が済んでいることも条件にする | 確かめた admin が 1 つの操作で、利用者の台帳を「有効」に戻し、admin の状態を「有効」にする (D9 の「有効にする」)。本人がパスワード + TOTP でサインインし直すと、admin の操作が通る |
| 監査 | 確かめた人・方法・日時と、戻した操作を残す (D12) | 同左 |

受信箱が侵害されたときの回復 (手順 4):
1. 止める: admin が台帳で停止 → AdminDisableUser → AdminUserGlobalSignOut。
2. 別経路で本人を確かめる: 招待のときに台帳に控えた連絡先 (組織の窓口の電話など) へ admin から連絡し、本人と組織の窓口に確かめる。メールでの申し出だけでは回復しない。確かめた人・方法・日時を監査に残す。
3. 受信箱の安全を確かめる: 本人 (または組織の窓口) が、メールのパスワードの変更と、転送や自動振り分けの設定の確認を済ませたことを確かめる。安全にできないときは、別のメールアドレスにする。
4. 宛先を変える (必要なとき): 再招待のときに新しいメールアドレスで作る。user_id は保つ。
5. 再招待: 手順 2 と同じく削除 → 作成 → 新しい sub を同じ user_id に結ぶ。台帳は停止のまま。乗っ取りの間に足されたパスキーとパスワードは、削除で消える (PoC 8)。
6. 台帳を有効に戻す: 上の「再招待の後の復帰」による。admin でない利用者では、この手順の 2 が、その「3 別経路の確認」に当たる。admin では、この手順の 2 (再招待の前の本人確認) に加えて、TOTP の登録の後に別の admin が別経路で本人を確かめ、登録の時刻 (`mfa_enabled_at`) を照合して有効にする (共通の表の admin の列のとおり。D9 の「有効にする」)。どちらも、加えて 3 (または 4) が済んでいること。戻すまでは、Cognito でサインインできても、SERVICE-PLATFORM の API は D9 の例外の 2 つを除いて 403 になる。

影響:

- 構成要件: admin-users に「停止」「再招待」(削除・作成・引き当ての付け替えを 1 操作に) を設ける。アカウントの画面にパスキーの一覧・追加・削除 (D1)。台帳に連絡先。
- 運用: 盗難の連絡を受けたら手順 2。受信箱の乗っ取りが疑われるときは手順 4 (別経路の本人確認と受信箱の安全確認を、再招待より先に行う)。
- 利用者: 再招待のメールが届いたら、初回と同じ手順で入り直す。admin には招待メールは届かず、一時パスワードを別経路で受け取る。

### D9. admin 操作の追加検証

- admin は TOTP を必須にする。admin を有効にするのは、別の admin が別経路で本人を確かめた後。
- admin はパスワード + TOTP でサインインする。

| 守り | 内容 |
| --- | --- |
| admin の第 2 要素 | admin グループの利用者は TOTP を必須にする (AdminSetUserMFAPreference で TOTP を有効・優先)。プールの MFA は任意でも、MFA を設定した利用者のパスワード サインインでは TOTP が毎回求められる |
| 現在状態の確認 | admin の API は毎回 Cognito の現在状態を確かめ、AdminGetUser の UserMFASettingList に `SOFTWARE_TOKEN_MFA` があることも確かめる (`ConfiguredUserAuthFactors` では見ない)。有効でない、admin グループに無い、TOTP が無い、のどれかなら 403 (fail-closed) |
| セッションの確認 | 設定の確認だけでは足りない。UserMFASettingList は今の設定で、提示されたトークンのサインインが TOTP を通ったことは示さない。admin の API は、トークンのセッションが TOTP を通ったことを確かめる。方式は (b) に決めた (下記) |
| レート制限 | WAF の web ACL を 2 つ。CloudFront (us-east-1 で作る) に IP ごとのレートベース ルール、ユーザープール (東京) に公開 API (InitiateAuth など) へのレートベース ルール。HTTP API には WAF を直接付けられないので CloudFront で受ける。加えて HTTP API のステージ・ルートのスロットリング、暗証番号の失敗回数 (D5)。最初は数える (Count) だけにして、検証用の負荷試験で閾値を評価してから止める (Block) に切り替える。ユーザープールの web ACL には、ChangePassword を最初から Block するルールも置く (D1) |
| 直叩き | `x-origin-verify` で CloudFront を通らない要求を 403 にする |
| 監査 | admin の操作は全件、user_id で記録する (D12)。構造化ログを 365 日保持する |

admin のセッションが TOTP を通ったことの確かめ方:

| 方式 | 扱い | admin の API が通す条件 |
| --- | --- | --- |
| (b) 台帳の `mfa_enabled_at` | 決定 | 台帳の admin の状態が「有効」で、トークンの `auth_time` (サインインした時刻) が `mfa_enabled_at` より後。`auth_time` は更新では変わらない (公式、PoC 10) ので、TOTP を登録する前にサインインしたセッションを更新しても通らない。`iat` (発行時刻) は更新のたびに新しくなるので、`iat` だけでは比べない |
| (a) `acr` / `amr` | 将来。PoC 6 の対象プールでは得られなかった (`TARGET_ACR_VALUES` は無視され、トークンに `acr` / `amr` が無い)。提供が来たら試し直す | ID トークンの `acr` が `urn:cognito:loa:4` (既定値。パスワード + TOTP) で、`amr` に `otp` と `mfa` がある。`acr` が無い、または低いトークンは 403。公式は段階的に提供中とする (Essentials 以上)。パスワードだけは `loa:1`、メールのコードだけは `loa:2`、パスキーは `loa:3`。更新しても `acr` / `amr` は引き継がれる (公式)。Amplify 6.20 は `TARGET_ACR_VALUES` を渡せないので、SDK を直接呼ぶ |

admin の状態の管理 (admin の API は台帳の admin の状態が「有効」でなければ 403。状態は 準備中 → 確認待ち → 有効、再招待すると 準備中 から):

| 場面 | 操作 | 結果 |
| --- | --- | --- |
| admin にする | admin (最初の 1 人は下の scripts) が admin グループに入れる。台帳の admin の状態は「準備中」、`mfa_enabled_at` は無し。admin の招待では招待メールを送らず (AdminCreateUser の `MessageAction=SUPPRESS`)、一時パスワードを別経路で渡す | admin の API は 403。アカウントの画面の TOTP の登録だけ使える (下の例外 1) |
| TOTP を登録する | 本人がアカウントの画面で登録 (Amplify の `setUpTOTP` → `verifyTOTPSetup` → `updateMFAPreference`) → 画面が「登録を終えた」API を呼ぶ → サーバが AdminGetUser で `SOFTWARE_TOKEN_MFA` を確かめ、`mfa_enabled_at` に今の時刻を書き、状態を「確認待ち」にし、AdminUserGlobalSignOut でそれまでのセッションを失効させる | まだ 403。本人はパスワード + TOTP でサインインし直して待つ |
| 有効にする | 本人以外の admin (最初の admin と緊急時は IAM の権限を持つ運用者が scripts で) が、別経路 (電話や対面) で、本人が登録したこと (登録の時刻 = `mfa_enabled_at` が本人の操作と合うこと) を確かめてから、状態を「有効」にする。再招待の後は、同じ操作で利用者の台帳も「有効」に戻す。確かめた人・方法・日時を監査に残す | ここから admin の操作が通る (下の「停止を解く条件」) |
| TOTP を失くした (紛失など) | 「TOTP の解除だけ」は使わない。本人以外の admin が、下の「再招待する」(D8 手順 2) を行う | 前のパスワード、TOTP、パスキーは利用者ごと消える (PoC 8)。前のトークンは、古い sub の行の無効の印で 403 になる |
| 再招待する (盗難、TOTP の紛失など。D8 手順 2 / 4) | 削除・作成し、admin グループに付け直し、`mfa_enabled_at` を消し、状態を「準備中」に戻す。一時パスワードは別経路で渡す。利用者の台帳は「停止」のまま | 前の「有効」は引き継がない。本人は下の例外 1 で「TOTP を登録する」まで進める。「有効にする」で、利用者の台帳と admin の状態を一緒に「有効」に戻す (D8 の「再招待の後の復帰」の admin の列) |
| TOTP を登録し直す | 本人が一時パスワードでサインインし、本パスワードを決め、TOTP を登録する。状態は「確認待ち」になり、上の「有効にする」を経て「有効」に戻る | 登録の前に得たセッションは、`auth_time` が新しい `mfa_enabled_at` より前なので 403 |
| 停止を解く条件 | 状態が「有効」(本人以外が別経路で確かめた)、TOTP が設定済み、`mfa_enabled_at` より後に TOTP を通ってサインインしたトークン、の全部 | 条件を満たした要求から admin の操作が通る |

停止中でも呼べる API (利用者の台帳が「停止」のときと、admin の状態が「準備中」のときの例外は、この 2 つだけ。ほかの API はすべて 403):

| API | 呼べる人 | すること |
| --- | --- | --- |
| 例外 1: TOTP の登録を終えた | admin グループに属し、admin の状態が「準備中」の本人。利用者の台帳が「停止」でもよい | 本人のトークンで呼ぶ。サーバは Cognito の現在の状態 (有効、admin グループ、`SOFTWARE_TOKEN_MFA`) を確かめ、自分の台帳の行に `mfa_enabled_at` を書き、admin の状態を「確認待ち」にする (上の「TOTP を登録する」)。ほかの行は書かない |
| 例外 2: 自分の状態を読む | サインインした本人 (状態を問わない) | 自分の台帳の状態 (有効 / 停止) と admin の状態を返す。画面が「停止中」「確認待ち」などを出すため。ほかの利用者のことは返さない |

- 再招待の前のトークンは使えない。再招待で古い sub の行に無効の印を付ける (D3) ので、古いトークンでは例外 1 も例外 2 も user_id を引けず 403 になる。
- admin でない利用者の復帰 (D8) では、SERVICE-PLATFORM の API を呼ばない (パスキーの登録は画面が Cognito を直接呼ぶ)。

- それでも残る危険:
  - 既に有効な admin のセッションを持つ者は、自分のアクセストークンで Cognito の公開 API から TOTP を外し、別の TOTP を付け直せる (推論)。この変更はサーバを通らず、台帳の状態も「有効」のまま変わらない。外している間は現在状態の確認で 403 になる。付け直した後は、(b) では外している間に TOTP なしで入ったセッションを見分けられない (外している間は、パスワードだけでなく、TOTP の間に登録したパスキーとメールのコードでも入れる。PoC 11)。admin のセッションを既に取られた後の話で、監査 (D12) とアカウントの CloudTrail (sub 付き。PoC 13) で見張る。提供が来たら (a) を試し直す理由の 1 つ。
  - パスワードと受信箱の両方を握られた場合 (または、一時パスワードの受け渡しや、TOTP の無い間のメールのコードでのサインインを横取りされた場合)、その者は自分の TOTP を登録して「確認待ち」まで進める。「有効」にする前の別経路の確認だけがこれを止める。確認が形だけになると通ってしまうので、確認では登録の時刻を本人の操作と突き合わせる。

最初の admin の作り方 (dev と本番の初回の起動も同じ):
1. IAM の権限を持つ運用者 (AWS の資格情報で scripts を流せる人) が、管理者作成用の運用ツールを流す。スクリプトは、(1) AdminCreateUser (一時パスワード、`email_verified=true`、招待メールは送らない `MessageAction=SUPPRESS`)、(2) 台帳に利用者の行と sub の引き当てを書く (user_id を採番)、(3) admin グループに入れ、台帳の admin の状態を「準備中」にする、(4) 監査に「scripts による作成」と実行した IAM の主体を残す。一時パスワードは別経路で本人に渡す。
2. 本人は一時パスワードでサインインし、本パスワードを決め、アカウントの画面で TOTP を登録する (上の表)。状態は「確認待ち」になる。
3. 運用者が別経路で本人の登録を確かめ、scripts で状態を「有効」にする (監査に残す)。本人がパスワード + TOTP でサインインし直すと、admin の操作が通る。
4. 2 人目からは、この admin が画面から招待し、「有効にする」もこの admin が行う。

全ての admin が TOTP を失くした (または使える admin がいない) ときの緊急の復旧:
1. IAM の権限を持つ運用者が、対象の admin が本人であることを別経路で確かめる。
2. 緊急用の scripts で、対象の admin を再招待する (D8 手順 2。TOTP の解除だけは使わない。回復の方針)。台帳で停止 → AdminDisableUser → AdminUserGlobalSignOut → AdminDeleteUser → AdminCreateUser (一時パスワード、`MessageAction=SUPPRESS`) → 新しい sub を同じ user_id に結ぶ (古い sub の行に無効の印) → admin グループに付け直す → `mfa_enabled_at` を消し、admin の状態を「準備中」に戻す。一時パスワードは別経路で渡す。
3. 監査に残す (実行した IAM の主体、対象、理由)。Cognito の管理 API の呼び出しは、CloudTrail にも残る (PoC 13)。
4. 本人が一時パスワードでサインインし、本パスワードを決め、TOTP を登録し直す (「確認待ち」)。
5. 運用者が別経路で本人の登録を確かめ、scripts で利用者の台帳と admin の状態を「有効」にする (監査に残す)。本人がサインインし直す。
- scripts を流す IAM の権限は、運用者だけに持たせる。

- パスキーだけを admin の条件にする案は採らない。パスキーはサインインさえできれば誰でも足せる (`associateWebAuthnCredential` はサインイン済みだけが条件)。パスワードやメールだけで入れる admin は、入った後で自分のパスキーを足せる。admin の入口の強さは、いちばん弱い入口で決まる。
- TOTP を設定した admin は、プールの MFA が任意のとき、パスキーとメールのコードでサインインできない (公式資料の表、PoC 5)。admin のサインインはパスワード + TOTP だけになる。admin もパスキーで入れるようにするには passkey MFA (`MULTI_FACTOR_WITH_USER_VERIFICATION`) が要る。組み合わせの挙動は未確認なので、追加の PoC の対象とする。

理由:

- threat protection (Plus) はレート制限をせず、公式に WAF を使うよう書かれている (参考資料)。

影響:

- 構成要件: admin-users の現在状態の確認に TOTP の確認と、セッションの確認 ((b)) を設ける。台帳に admin の状態と `mfa_enabled_at`。「TOTP の登録を終えた」(停止中でも呼べる例外 1)「自分の状態を読む」(例外 2)「admin を有効にする」(別経路の確認の記録つき。再招待の後は利用者の台帳も戻す) の API。admin のパスワードの変更 (別の admin の AdminSetUserPassword。D1)。WAF の web ACL 2 つ (edge と core。core に ChangePassword の Block)。HTTP API のスロットリング。アカウントの画面に TOTP の登録 (admin のみ)。管理者作成用の運用ツールを用意し (招待・台帳・グループ・監査。招待を管理者に限定する)、緊急の復旧用のスクリプトを設ける。
- 運用: admin を増やす手順は「一時パスワードで招待 (招待メールは送らず別経路で渡す) → 本パスワード → admin グループ (準備中) → 本人が TOTP を登録 (確認待ち) → 別の admin が別経路で確かめて有効にする → サインインし直す」。TOTP を失くした admin は、別の admin が再招待し (D8 手順 2。一時パスワードは別経路で渡す)、本人が登録し直し、別の admin が確かめて有効に戻す。使える admin がいなければ緊急の復旧。
- 利用者: お客様には影響なし。

### D10. 通知元と添付領域の境界

- 通知キューは許可したサービスの IAM ロールからだけ送信できる構成とする。
- notifier は SQS が付ける SenderId とサービスの対応表を照合し、本文の app と一致する場合だけ、そのサービスの S3 接頭辞から添付を取得する。送り手自身が指定する本文・MessageAttributes は、送り手の証明として使わない。
- 宛先はサービスごとの許可ポリシーで検証する。宛先の範囲を変えるときも、通知元と添付領域の照合を要件とする。
- 代替案はサービスごとにキューを分け、キューポリシーで送り手を限定する方式。資源数と運用する受け口が増えるため、共通キューでは SenderId の照合を採る。
- サービス追加時は送信元ロールと宛先ポリシーを登録し、不一致の要求が配送されないことを試験する。

### D11. 利用者とサービスの移行方針

- 少数利用者の移行には再招待を採用し、認証要素を移植しない。必要な利用者情報と業務上の user_id を対応付ける。
- ログイン記録は移さず、新しい環境で機器認証を行う。
- 機器単位で「移行元の処理を終了 → 移行先の利用期間を開始 → 割当と許可 → サービス開始」の順に切り替える。同じ機器を両方で同時に処理しない。
- 切替後は移行元のアクセスを停止する。処理・通知の二重実行がないことを確認し、履歴の保持条件を記録する。

この手順は独立した認証領域へ移行する場合の設計例であり、特定の稼働環境の移行実績を示さない。

### D12. 監査

- 誰が・いつ・どの機器に・どのサービスで・何をしたかを、user_id で残す。請求の実績の基礎にする。
- 記録項目: user_id、操作時点の email、役割、操作、サービス、機器アカウント、device_period_id、assignment_id、サービス固有の対象 ID、結果、送信元 IP、user_agent、UTC の時刻。暗証番号・トークン・業務本文は記録しない。
- 記録する操作: 機器ログインの成否、招待・停止・再招待・復帰、別経路の本人確認、属性変更、利用期間・割当・許可の変更、TOTP 登録、管理者の有効化、運用ツールによる作成・回復、各サービスの重要な操作。
- core の監査テーブルは台帳から分離し、user_id と機器アカウントの両方で検索できるようにする。各サービスには監査への追記だけを許可し、構造化ログも 365 日保持する。
- パスキーの追加・削除 (と D1 のパスワードの後付け): 画面 (Amplify) が Cognito を直接呼ぶ (StartWebAuthnRegistration / CompleteWebAuthnRegistration / DeleteWebAuthnCredential、ChangePassword)。SERVICE-PLATFORM の API を通らないので、監査テーブルには残らない。追う手段はアカウントの CloudTrail にする。
  - 4 つの呼び出しは管理イベントとして記録され、`additionalEventData.sub` で利用者が分かる。トークンとパスワードは隠される。DeleteWebAuthnCredential には credentialId が残り、登録には残らない。プールの ID はイベントに無いので、sub で引く (PoC 13)。
  - sub から user_id を引くため、再招待で古い sub の行を消さず、無効の印を付けて残す (D3)。
  - イベント履歴 (lookup-events) は 90 日まで。長く残すにはアカウントの証跡に頼る。WAF で止めた要求は、PoC の検索の時点と時間窓では検出しなかった。止めた記録は WAF のログで見る。
  - 画面が成功の後に SERVICE-PLATFORM の API へ知らせて監査に書く案は作らない。最善努力で欠けるうえ、CloudTrail で追えるため。
- 追記だけの仕組み: IAM で絞れるのは操作の種類 (`PutItem`) までで、`PutItem` は同じキーの既存の行を置き換えられる。そのため `audit.emit` は `ConditionExpression: attribute_not_exists(PK)` を付け、SK に推測できない ID (ULID) を入れて、既存の行を上書きさせない。
- 保持: 操作の記録は 365 日 (TTL)。請求の実績の基礎になる記録 (通信機の利用期間の開始・終了、サービスの許可の開始・終了、割り当ての変更、サービス固有の利用期間の開始・終了) は期限を付けない。

理由:

- 監査を台帳とは別のテーブルにするのは、台帳を読み取り専用に保ちつつ、全サービスが監査を残せるようにするため。

影響:

- 構成要件: core に監査テーブルを足し、名前を SSM で公開する。shared レイヤに監査の書き込み (`audit.emit` 相当。監査テーブルへの `PutItem` だけ) を置き、全 API から呼ぶ。監査の閲覧には管理者権限を要求する。
- 運用: 集計を再構築できるよう、請求の根拠となる記録を保持する。
- 利用者: なし。

利用者単位の操作追跡と請求の根拠を残すことが監査の目的である。台帳と監査を分け、サービスには台帳の読取りと監査の追記だけを許可する。

| 8 | AdminDeleteUser でパスキーも消えること | D8 | 確認できた。作り直すと要素は EMAIL_OTP だけで、前のトークンは UserNotFoundException |
| 9 | 招待とメールのコードが SES から届くこと | D1 | 確認できた。PoC のテスト用受信箱で到達を観測。文面は既定の英文 |

- 仮想認証器による検証であり、実機のスマホ、同期パスキー、実機固有の表示は検証していない。
- localhost で実施した。同一 origin のセッション共有は確認したが、公開用 FQDN、CloudFront の behavior とフォールバックは検証していない。
- acr / amr が得られなかった結果は対象プールに限る。他の Cognito 環境全体へ一般化しない。
- rotation は猶予 0 秒、ALLOW_USER_AUTH のみで試した。採用した猶予 30 秒、SRP 併用、複数タブの同時更新は追加検証の対象とする。
- WAF 下の初回パスワード変更は TOTP 設定前の admin 役で試した。TOTP を保持したままの再設定の順序は、この PoC の確認範囲に含めない。
- 台帳と業務 API の認可は PoC に含まない。古い JWT を API 側で拒否すること、admin の状態と auth_time の照合は結合試験の要件とする。
- ハーネスは一部の返り値や CloudTrail の属性、allowCredentials の不明な項目の詳細を保存していない。保存済みの結果、手動観察、推論を検証記録で区別する。

## 代替案

| 案 | 評価 |
| --- | --- |
| 外部 IdP のアカウントを業務識別子として直接利用 | 業務上の user_id と認証のライフサイクルを分離できる専用プールを採用 |
| 自前の認証・WebAuthn 検証 | 認証情報の保管と検証の責任が増えるため、IaC と Amplify に統合できる Cognito を採用 |
| 一時パスワードで一般利用者を招待 | パスワードの入口を残すため、メールコードでの初回認証とパスキー登録を採用 |
| セッションを sessionStorage に保存 | タブ間の操作性を考慮して localStorage と期限・rotation を採用。どちらも XSS 対策が必要 |
