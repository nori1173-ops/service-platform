> サインイン、利用者の識別、通信機ログイン、サービス許可、管理操作の認証を定める。PoC を踏まえた判断 12〜16、グループと access の判断 17〜19、管理者の二つの入口の判断 20 を収録する。

## 背景

顧客単位・利用者単位で操作を追跡し、利用に応じた請求の根拠にできる独立した認証が必要である。新しい基盤ではパスワードに頼らず、パスキーを標準にする。招待、紛失・侵害からの回復、管理操作、機器の利用主体の変更までを共通の認可モデルで扱う。

複数のサービスで、本人の認証と業務上の利用許可を共通化する。Cognito の sub と業務の user_id を分離し、再招待後も割り当てと履歴を保つ。フィッシングへの耐性を重視し、パスキーを標準の入口として採用する。

## 決定事項 (Decision)

全体の流れ (図は文字の図。動線はユーザー決定。`[判断 n]` は 2026-11-02 の判断で決めた部分):

```text
サインイン（パスキー優先）
  ├─ 機器単位 → 割当確認・機器ログイン → 許可されたサービス
  └─ アカウント単位 → パスキーの管理・割当と許可の一覧・管理機能

サーバ側の確かめ方 (D3〜D5、D9):

```text
要求 --> JWT (署名・期限・aud) --> sub --> user_id (台帳) --> 利用者が有効か
     --> [通信機を伴う API] 通信機の稼働中の利用期間 P --> P での自分の割り当て (有効期間内)
                            --> ログイン記録 (同じ assignment_id、valid_from 以後、12 時間)
     --> [サービスの API]   サービスの許可 (P に属し、期間内)
     --> [admin の API]     登録後のセッションと現在の TOTP・admin の状態か (D9)
     --> 処理 --> 監査 (user_id で記録)
```

2026-11-05 の追記: D13 / D14 ( で実装) で、(2) を「P を扱う根拠がある」(本人宛の割り当て、グループ宛の割り当て、P の access が everyone のどれか) に広げ、(3) のログイン記録をその根拠に紐づける。(1) と (4) は変えない。

### D1. 専用のユーザープール、サインインの方式、トークン

- 認証は専用の Cognito ユーザープール。他システムのプールを借りない。
- パスキーを優先する。
- お客様はパスワード無しで作成し、初回と回復はメールのコード (EMAIL_OTP)、常用はパスキー。admin は初回にパスワード + TOTP を設定し、有効化後にパスキーを登録すれば、以後は本人確認つきのパスキーでも入れる (判断 6 / 20)。初版より前の決定「パスワードは招待と回復のために残す」は、お客様についてはこの判断で替わった。
- トークンは ID / アクセス 60 分、更新 24 時間、保存場所は localStorage (判断 7)。
- 1 人の利用者がパスキーを複数登録できる (PC に 1 個、スマホに 1 個など。判断 11)。

- 機能プランは Essentials (`UserPoolTier: ESSENTIALS`)。パスキーは Lite では使えない。Plus は使わない。
- サインインは choice-based (USER_AUTH)。アプリクライアントの ExplicitAuthFlows は `ALLOW_USER_AUTH`。`ALLOW_REFRESH_TOKEN_AUTH` は外す。`ALLOW_USER_SRP_AUTH` は、admin の SRP サインインを使う構成では残す。`ALLOW_USER_AUTH` がパスワードと SRP を含むので、残しても攻撃の入口はほとんど増えない (推論)。
- 画面はパスキー (`WEB_AUTHN`) を第一候補として求める (Amplify の `signIn` に `authFlowType: 'USER_AUTH'`、`preferredChallenge: 'WEB_AUTHN'`)。パスキーを持たない利用者には Cognito が候補の一覧 (SELECT_CHALLENGE) を返すので、画面は候補から選ばせる。
- パスキーの前にユーザー名 (メールアドレス) が要る。入力欄の自動補完 (autofill) では始められない (推論)。前回のメールアドレスをブラウザに覚えておく。
- サインインの要素 (`SignInPolicy.AllowedFirstAuthFactors`) は `PASSWORD`・`WEB_AUTHN`・`EMAIL_OTP` (下の案 B)。`PASSWORD` は外せない。`WEB_AUTHN` だけにもできない。
- パスキーの設定: RP ID は D7。利用者の確認 (`WebAuthnUserVerification`) は `required` (指紋・PIN などの本人確認を伴う認証器だけ)。`WebAuthnFactorConfiguration` は既定の `SINGLE_FACTOR`。
- MFA はプールで任意 (`MfaConfiguration: OPTIONAL`、TOTP だけ)。TOTP を持つのは admin だけにする (D9)。必須 (ON) にしないのは、必須にするとメールのコードが使えず、パスキーも passkey MFA を有効にしたときしか使えないため。
- パスキーはサインイン後にだけ登録できる。招待した利用者には managed login も登録を促さないので、初回サインインの直後に画面から登録を促す。1 人で複数持てる (下の「パスキーの複数登録」)。
- 注記 (2026-11-05、): サインインの直後の着地は D5 の近道に従う。メールのコードで入ったパスキーの無い利用者には、近道より先にアカウントの画面で登録を促す (今のまま)。セッションが残っていればパスキーの確認は出ない (今のまま)。

決定 (PoC の結果を受けた設計判断、2026-11-02):
- 更新トークンの rotation を採る (判断 14)。`RefreshTokenRotation` は `Feature: ENABLED`、`RetryGracePeriodSeconds: 30`。
- お客様のパスワードの後付けは、ユーザープールの web ACL で ChangePassword を Block して止める (判断 15)。下の「パスワードの後付け」。

パスキーの複数登録:
- 1 人の利用者 (独自の user_id、Cognito の 1 利用者) が、パスキーを複数登録できる。PC に 1 個、スマホに 1 個のように、端末ごとに登録する使い方を想定する。
- 上限は 1 利用者あたり 20 個 (Cognito の制限で、変えられない。参考資料)。上限に達したら、使わなくなったものを消してから足す。
- アカウントの画面の「パスキーの管理」(D5) で、本人が次を行う。
  - 一覧: 登録済みのパスキーごとに、名前・登録日・認証器の種類を出す。Amplify の `listWebAuthnCredentials` (Cognito の ListWebAuthnCredentials) が `friendlyCredentialName`・`createdAt`・`authenticatorAttachment` を返す (PoC は Amplify 6.20 を使用)。認証器の種類は `platform` (端末に組み込みの認証器。内蔵の指紋センサーなど) か `cross-platform` (端末とは別の機器。Bluetooth のセキュリティキーなど)。Cognito はこの項目を返さないことがある (必須の項目でない) ので、無ければ空欄にする。
  - 追加: `associateWebAuthnCredential` (サインイン済みのときだけ使える)。端末を設けるときは、その端末でサインインして (メールのコードなど) から登録する。同じ認証器に 2 つ目は作れない (Cognito が登録済みの一覧 `excludeCredentials` を渡し、ブラウザが断る。PoC 12)。
  - 削除: `deleteWebAuthnCredential` で 1 件ずつ消す。消せるのは本人だけ (D8)。
- 名前: Cognito が登録のときに自動で付ける (`FriendlyCredentialName`。公式の説明は「自動で生成した名前」)。登録の API (CompleteWebAuthnRegistration) の要求はアクセストークンと認証器の応答だけで、名前を渡す項目は無い。Amplify の `associateWebAuthnCredential` も引数を取らない。付け替える API も無い (WebAuthn の API は登録の開始・完了、一覧、削除の 4 つ)。自動の名前は端末の名前ではなく、種類の名前 (Device-bound Passkey / Roaming passkey) だった (PoC 12)。画面は種類の名前と登録日時を出す。利用者が付ける名前を表示する場合は、credentialId ごとの台帳で管理する。
- 推奨する運用: 端末ごとに 1 個 (PC とスマホ) を登録しておく。1 台を失くしても、もう 1 台で入れる (締め出されにくい)。失くした端末のパスキーは、もう 1 台から消せる (D8 手順 1)。盗難が疑われるときは D8 手順 2 による。どの端末も使えないときの回復は、メールのコードで行う。
- 有効な admin もアカウントの画面でパスキーを登録し、通常の入口 (`/login`) から入れる。パスワード + TOTP の入口 (`/login/admin`) も残す。TOTP の登録・別経路の確認・有効化は省略しない (D9、判断 20)。

招待と回復の 2 案 (案 B を採用):

| 観点 | 案 A: 一時パスワードで招待 | 案 B: パスワード無しで招待 (採用) |
| --- | --- | --- |
| 招待 | AdminCreateUser。一時パスワードをメールで送る | AdminCreateUser で一時パスワードを省く。招待メールに一時パスワードを入れない |
| 初回 | 一時パスワード → 本パスワードを決める → パスキーを登録 | メールのコード (EMAIL_OTP) でサインイン → パスキーを登録 |
| 常用 | パスキー。パスワード欄は画面に出さない | パスキー |
| パスキーを失くしたとき | パスワードでサインイン → 登録し直す | メールのコードでサインイン → 登録し直す |
| パスワード | 残る。後から消せない。画面で隠しても、API を直接呼べばパスワードでサインインできる | 作成のときは持たない。本人が後から足す入口は Cognito の設定では止められないので、web ACL で止める (下の「パスワードの後付け」、WAF の方針) |
| 受信箱への依存 | パスワードの再設定をメールで行うなら、受信箱が回復の要になる | 受信箱が回復の要になる (メールを取られると乗っ取られる) |
| 前提 | USER_AUTH 経由で一時パスワードの変更 (NEW_PASSWORD_REQUIRED) に進む (PoC 4) | EMAIL_OTP は Essentials と SES 送信 (`EmailSendingAccount: DEVELOPER`) が要る。MFA を設定した利用者はメールのコードを使えない |

- 案 B を採った理由: (1) パスワードは一度持たせると消せない。案 A から案 B へ移るには利用者を作り直すことになる。逆に案 B の利用者には後からパスワードを足せる (AdminSetUserPassword、推論)。(2) 案 A では全員がパスワードを持ち、「パスワードは招待と回復だけ」を Cognito では強制できず、画面で隠すだけになる。案 B では、本人が自分で足さない限りパスワードを持たない。(3) SERVICE-PLATFORM がパスワードを持たせるのは admin だけになり (パスワード + TOTP)、パスワードを持つ役割を限定できる (D9)。
- 案 B でも、サービス提供者の admin は一時パスワードで招待し、パスワード + TOTP でサインインする (D9)。プールは PASSWORD を常に持つので、パスワード有りと無しの利用者を混ぜられる。
- 回復の設定 (`AccountRecoverySetting`) は `admin_only`。パスワード無しの利用者の「パスワードを忘れた」(ForgotPassword) は、この設定で止まる (PoC 3)。admin のパスワードの回復は、別の admin が一時パスワードを設定して渡す (AdminSetUserPassword、`Permanent=false`)。`admin_only` が止めるのは「パスワードを忘れた」からの回復で、サインイン済みの本人がパスワードを設けること (下) は止めない。

パスワードの後付け (お客様):
- 事実: ChangePassword は本人のアクセストークンで呼ぶ公開 API で、IAM では絞れない。パスワードを持たない利用者は、前のパスワード (`PreviousPassword`) を省いて新しいパスワードを設定できる (公式)。`PASSWORD` はサインインの要素から外せない (参考資料)。
- このため、「作成のときはパスワードを持たない」 は保てるが、「その後もパスワードの入口が無い」とは言えない。SDK を直接呼べば、サインインできる本人 (または本人のセッションを得た者) はパスワードを足せ、足した後は `PASSWORD` でもサインインできる (PoC 14。Amplify の `updatePassword` は旧パスワードを求めて手前で止めるだけ)。これを Cognito の設定だけで防ぐ手段は無い。
- 方針:
  - SERVICE-PLATFORM の画面には、お客様向けのパスワードの設定・変更と、パスワードでのサインインを出さない。
  - 塞ぐ: ユーザープールの web ACL で、`x-amz-target` が `AWSCognitoIdentityProviderService.ChangePassword` の要求を Block する。dev と本番の両方に、最初から Block で置く 。PoC 14 で 403 になり、ほかの公開 API、パスキーのサインイン、admin の招待 (一時パスワード → 本パスワード)、TOTP の登録、AdminSetUserPassword は止まらなかった。
  - admin 自身のパスワードの変更: ChangePassword を使わない。別の admin が AdminSetUserPassword (`Permanent=false`) で一時パスワードを出し、本人が NEW_PASSWORD_REQUIRED で決め直す。
  - 見つける手段: admin は AdminGetUserAuthFactors の `ConfiguredUserAuthFactors` で、利用者が `PASSWORD` を使えるかを見られる (公式)。後付けした利用者に `PASSWORD` が出ることを PoC 14 で確かめた。admin-users の利用者の画面に出す。

トークンの有効期間と保存場所の比較 (T2 を採った。トークンの方針):

| 案 | ID / アクセス | 更新の期限 | 保存場所 | 利便 | API を呼べる最長の時間と保存データ |
| --- | --- | --- | --- | --- | --- |
| T1 | 60 分 | 30 日  | localStorage (Amplify の既定) | 月に 1 回のサインイン | サインインから 30 日 + 60 分。保存データはサインアウトまで残る |
| T2 (採用) | 60 分 | 24 時間 | localStorage | 1 日に 1 回のサインイン。新しいタブや同一 origin の別ビルドでも同じセッション | サインインから 24 時間 + 60 分。保存データはサインアウトまで残る |
| T3 | 60 分 | 12 時間 | sessionStorage | タブを閉じるたび、新しいタブ (通知メールのリンクなど) を開くたびにサインイン | タブを開いたままなら 12 時間 + 60 分。タブを閉じると保存データが消える |

- 期限の読み方: 更新トークンの期限は最初のサインインから数え、更新しても延びない。更新で得られるのは新しい ID / アクセストークン (60 分) で、期限の直前に更新すると、そのトークンがさらに 60 分使える。localStorage の保存データは期限が過ぎても自動では消えず、サインアウト (Amplify の `signOut`) で消える。共用の端末では、使い終えたらサインアウトする (画面にサインアウトを常に出し、案内にも書く)。
- XSS の残余リスク: localStorage も sessionStorage も同じ origin のスクリプトから読める。XSS が成立すれば、どちらに置いても更新トークンを含むトークンを読まれ、更新の期限まで使われうる。CSP  は XSS を起こしにくくする軽減策で、保証ではない。読まれた後の被害は、更新の期限、台帳の停止 (D3)、AdminUserGlobalSignOut (更新トークンの失効) で区切る。
- 更新トークンを使うたびに新しいものへ替える rotation を採る (AWS の推奨。判断 14)。Amplify 6.20 は `GetTokensFromRefreshToken` で更新し、古い更新トークンの再利用は `RefreshTokenReuseException` になる (PoC 10)。`REFRESH_TOKEN_AUTH` とは併用できないので、ExplicitAuthFlows から `ALLOW_REFRESH_TOKEN_AUTH` を外す。猶予 (`RetryGracePeriodSeconds`) は 30 秒にし、複数のクライアントからの再試行を考慮する。rotation でも期限は最初のサインインから延びず、`auth_time` も変わらない (PoC 10)。
- T2 を採った理由: (1) パスキーなら毎日のサインインは指 1 本で済み、30 日も要らない。(2) 保存場所を sessionStorage にしても XSS の被害は変わらない (上の残余リスク)。違いは、タブを閉じたときに保存データが消えるかどうか。(3) sessionStorage は新しいタブで切れる。(4) 利用停止は台帳で即時に効かせる (D3) ので、取り消しのためにアクセストークンを短くする必要は無い。
- Amplify v6 で sessionStorage にする方法は `cognitoUserPoolsTokenProvider.setKeyValueStorage(sessionStorage)` (Amplify 公式)。

理由:
- パスキーは Essentials 以上と USER_AUTH でしか使えない (調査ノート Q1)。
- 料金は Essentials 0.015 USD / MAU / 月、月 10,000 MAU まで無料 (アカウントまたは Organization 単位。同じアカウントの他のプールと分け合うと推論)。無料枠を使い切っていても 100 MAU で月 1.50 USD (調査ノート Q5、AWS Pricing MCP)。

影響:
- 実装: infra/core の UserPool と UserPoolClient を作り替える (階層、SignInPolicy、WebAuthn の 3 項目、ExplicitAuthFlows、AccountRecoverySetting、トークンの期間、rotation、web ACL)。`auth.ts` に USER_AUTH の分岐 (パスキー、メールのコード、候補の選択) とパスキーの登録・一覧・削除 (1 人で複数。一覧に名前・登録日・認証器の種類) を足す (Amplify 6.10.0 以降。土台は 6.20)。
- 運用: 招待と EMAIL_OTP のメールは SES から送り、日本語の文面で登録とサインインを案内する。
- 利用者: 初回はメールのコードでサインインし、続けてパスキーを登録する。端末ごと (PC とスマホなど) にパスキーを足せる。端末を替えたら、新しい端末でサインインし直して (メールのコードなど) 登録し、古いものを消す。

### D2. 招待制と email 属性の守り

- 自己登録は作らない。招待制だけにする (判断 10)。

- `AdminCreateUserConfig.AllowAdminCreateUserOnly: true` で、プールが自己登録 (SignUp) を受け付けない。
- 招待では AdminCreateUser に `email` と `email_verified=true` を渡す。メールの宛先は admin が入力し、admin でない利用者 (お客様と社員) は届いたメールのコード (EMAIL_OTP) でサインインして受信を示す。EMAIL_OTP のサインインに成功すると `email_verified` が true になる。admin には招待メールを送らず、一時パスワードを別経路で渡す (D9)。
- email は利用者が書き換えられないようにする。
  - スキーマで email を必須にしない。必須の属性は、WriteAttributes から外しても、どのアプリクライアントからも書ける。必須かどうかはプールを作った後で変えられない。core テンプレートも必須から外した。email を利用者名にしたまま必須を外せる (PoC 1)。
  - UserPoolClient の WriteAttributes を明示し、`email` と `email_verified` を入れない。明示しないと全ての標準属性が書ける。
  - `UserAttributeUpdateSettings.AttributesRequireVerificationBeforeUpdate: [email]`。万一 email が更新されても、検証されるまで旧い値が有効のまま残る。
  - WriteAttributes に入れなければ、利用者は `email_verified` も `email` も書けない (PoC 2)。
- email を変えるのは admin だけ (AdminUpdateUserAttributes で `email` と `email_verified=true`)。変えたことは監査に残す (D12)。

理由:
- 招待制を採り、自己登録の入口を設けない (判断10)。
- 利用者名がメールアドレスなので、email を書き換えられると別人のメールアドレスで振る舞える。招待制の意味も薄れる 。

影響:

- 構成要件: core テンプレートの Schema、AdminCreateUserConfig、UserAttributeUpdateSettings、PreSignUp の関数、UserPoolClient の WriteAttributes を設定する。テンプレートのテストを設ける。
- 運用: 社員も admin が招待する。メールアドレスの変更は admin への依頼になる。
- 利用者: 自分でメールアドレスを変える画面は無い。

実装の補足 (2026-11-05): 招待リンクの `/login#email=` で宛先を補完する。前回のアドレスより優先し、読み取ったら URL から消す。SES のクリック追跡を有効にしない。EMAIL_OTP のコードは 8 桁、コードのメールにはリンクを入れない。

メールアプリ内のブラウザでは、コードのメールを見るために閉じるとサインインの途中状態が消える。 で招待とコード画面に標準ブラウザで開き、コード画面を閉じない案内を追加した。マジックリンク (Cognito のカスタム認証によるリンクだけで入る方式) は dev  で検討する。

### D3. 利用者の識別子 (独自 user_id)

- 利用者の識別子は独自の user_id を挟み、認証方式に依存させない。

- user_id は ULID (利用期間 period_id と同じ形式)。招待のときに台帳で採番する。
- 台帳に「利用者」の行 (user_id ごと) と「sub の引き当て」の行 (sub → user_id) を持つ。API は検証済みのトークンの sub から user_id を GetItem で引く (強い整合の読み取り)。
- 再招待 (AdminDeleteUser → AdminCreateUser) で sub が変わっても、新しい sub を同じ user_id に結び直す。古い sub の行は消さず、無効の印を付けて残す。CloudTrail の `additionalEventData.sub` から後で user_id を引くためである。API の引き当ては、無効の印の付いた行を「引けない」として扱う (403)。
- 業務データ（割当、ログイン記録、監査、サービス設定の操作者）はすべて user_id で保持する。
- 台帳の利用者に「状態」(有効 / 停止) を持ち、全ての API が毎回確かめる。停止中でも呼べる API は、D9 の「停止中でも呼べる API」の 2 つだけ。Cognito の無効化と合わせて使うと、発行済みのトークンが期限内でも即時に止まる。
- Cognito のカスタム属性に user_id を入れる案は採らない。カスタム属性は追加すると消せず、引き当ては台帳で足りる。

理由:
- 調査ノート Q3 のとおり、admin が他人のパスキーを消す API は無い。紛失・乗っ取りへの代わりの手段は「削除して再招待」で、そのとき sub が変わる。sub を業務データの鍵にすると、再招待のたびに付け替えが要る。
- 旧の JIT ユーザー名は発行元と sub に依存していた 。

影響:

- 構成要件: 台帳 (D4) と shared レイヤの認証 (`auth.py`) に「sub → user_id と状態の確認」を設ける。admin-users の識別子を sub から user_id に替える。
- 運用: 再招待は admin-users の操作 1 つにまとめる (削除、作成、引き当ての付け替えと古い sub の行の無効の印、admin グループの付け直し。admin なら admin の状態を「準備中」に戻す。台帳は有効に戻すまで停止のまま。D8)。
- 利用者: 再招待されても、通信機の割り当てと履歴は残る。

### D4. 役割と許可のモデル

- 許可は弊社 admin が出す。サービスは通信機の利用期間に結び付ける。
- 許可を出すのは基盤の admin だけ。役割の列を持ち、組織の管理者は後で足せる形にする (判断 2)。
- 通信機の割り当てと暗証番号の両方を許可の条件にする (判断 9)。
- 改め (2026-11-05): 割り当てを条件にするのは、access が assigned の通信機の利用期間だけにした。既定の everyone では、台帳の有効な利用者なら誰でも通信機ログインに進め、暗証番号が門になる (D14、判断 18)。割り当ての相手にグループを足した (D13、判断 17)。下の条件 (3) は、ログイン記録の根拠 (種類・ID・世代) が今の (2) の根拠の集合に含まれるかで確かめる形に改め、ログインの時刻と valid_from の比較をやめた (D14)。

- 役割: 弊社 admin は Cognito の admin グループ (正本は Cognito)。お客様と社員は「利用者」(グループ無し)。許可の管理は基盤の admin が行う (判断 2)。台帳の割り当ての行に「役割」の列を持ち、後で組織の管理者を足せるようにする。
- 「通信機の利用期間」を台帳に持つ。1 台の通信機アカウントを 1 つのお客様 (組織) が使う期間で、開始・終了・組織名を持つ。同じ通信機アカウントで稼働中の通信機の利用期間は 1 つだけ (条件付きの書き込みで守る)。
- 割り当て・サービスの許可・ログイン記録は、すべて通信機の利用期間に結び付ける。
  - 割り当て: 利用者 × 通信機の利用期間。割り当てごとに assignment_id (ULID) を採番し、有効期間 (valid_from / valid_to) を持ち、通信機の利用期間の中に収める。利用者ごとに先に終えることもできる。付け直すときは新しい assignment_id にし、前の行を上書きしない。
  - サービスの許可: サービス × 通信機の利用期間。開始・終了を持ち、通信機の利用期間の中に収める。
  - ログイン記録: 割り当てに紐づける (assignment_id、通信機の利用期間の ID、user_id、ログインの時刻を持つ)。期限は 12 時間 (D5)。
- 許可の単位は「サービス × 通信機の利用期間」(下の表の案 A)。
- API が通す条件 (全部を満たすときだけ): (1) 通信機アカウントに稼働中の通信機の利用期間 P がある。(2) 利用者の割り当てが P に属し、今が有効期間内。(3) ログイン記録の assignment_id が (2) の割り当てと同じで、ログインの時刻が割り当ての valid_from 以後、かつ期限内。(4) サービスの API では、サービスの許可が P に属し、今が期間内。どれか 1 つでも欠ければ 403。前の通信機の利用期間に属する割り当て・ログイン記録・許可は、(1)〜(4) のどれかを満たさない (割り当ては (2)、ログイン記録は (3)、許可は (4) で落ちる)。
- 利用者には、扱える通信機を admin が割り当てる。通信機の操作は「割り当て」と「暗証番号の照合」の両方を条件にする (判断 9)。台帳に利用者の種別・組織名・備考と通信機の割り当てを持つ。
- 台帳は DynamoDB の 1 テーブル。core スタックに置き、名前を SSM で公開する。書くのは admin-users と通信機ログインの API、読むのは各サービスの API (shared レイヤ経由)。

許可の単位の比較:

| 案 | 内容 | 長所 | 短所 |
| --- | --- | --- | --- |
| A サービス × 通信機の利用期間 (採用) | admin が「通信機アカウント X をお客様 O が使う期間」を作り、その中で「サービス S を開始日から終了日まで」許可する。割り当てとログイン記録も同じ期間に属す | 通信機は前のお客様の利用が終わった翌日に次のお客様へ渡ることがある 。通信機の利用期間を終えれば、属する割り当て・ログイン記録・許可がまとめて効かなくなり、前のお客様の許可が残らない。期間がそのまま請求の実績の基礎になる。サービスの一覧 (通信機ログインの後) を素直に出せる | 期間を 2 段で持つ (通信機の利用期間と個別サービスの単位)。admin の操作が 1 つ増える |
| B サービス × 利用者 | admin が「利用者 U にサービス S を」許可する | 単純 | 通信機と結び付かない。通信機が他のお客様に渡っても許可が残る。通信機ごとの実績を残せない |
| C サービス固有の利用期間 | 個別サービスの利用開始を許可とする | サービス内で完結する | 共通の通信機・サービス一覧を構成しにくい |

台帳は core の DynamoDB テーブルに置き、名前を SSM で公開する。admin-users と機器ログイン API が書き、各サービスは shared レイヤ経由で読む。

| データ | PK | SK | 主な項目 |
| --- | --- | --- | --- |
| 利用者 | `USER#{user_id}` | `PROFILE` | sub、email (控え)、状態 (有効 / 停止)、種別 (社員 / お客様)、組織名、連絡先 (別経路の本人確認に使う。D8)、備考、admin の状態と mfa_enabled_at (admin のみ。D9)、作成者 (user_id)、作成・更新日時 |
| sub の引き当て | `SUB#{sub}` | `USER` | user_id、無効の印 (再招待で古くなった sub。行は消さない。判断 16) |
| 通信機の利用期間 | `DEVICE#{account}` | `DPERIOD#{device_period_id}` | device_period_id (ULID)、組織名、開始・終了、状態 (稼働中 / 終了)、始めた人、終えた人。稼働中の 1 つは `DEVICE#{account}` / `CURRENT` で指す |
| 割り当て | `DPERIOD#{device_period_id}` | `USER#{user_id}#{assignment_id}` | assignment_id (ULID)、valid_from・valid_to、製造番号 (初回の通信機ログインの成功時に保存。旧の「利用者の控え」の代わり)、役割 (利用者)、割り当てた人、日時 |
| 割り当ての逆引き | `USER#{user_id}` | `ASSIGN#{device_period_id}#{assignment_id}` | 通信機アカウント、valid_from・valid_to (上の写し、または GSI) |
| サービスの許可 | `DPERIOD#{device_period_id}` | `GRANT#{service}#{grant_id}` | grant_id (ULID)、開始・終了、状態、許可した人、終えた人 |
| 通信機ログインの記録 | `USER#{user_id}` | `LOGIN#{account}` | assignment_id と device_period_id (ログインしたときの割り当て)、ログインの時刻、期限 (12 時間)、手段 (前回値 / 最新値)、通信機設定の要約 |
| 照会の失敗回数 | `DEVICE#{account}` | `PINFAIL` | 回数、数え始め、止める期限 |
| 監査 | (台帳には置かない) | (台帳には置かない) | 台帳とは別の core の監査テーブルに置く (D12) |

理由:
- 通信機の「主語」は旧と同じく通信機アカウントと暗証番号だが、暗証番号は 4 桁で、現場で共有されることもある。割り当てがあれば「誰がどの通信機を扱えるか」が台帳で分かり、請求の実績を user_id と通信機で残せる。
- 「暗証番号だけで任意の通信機に入れる範囲を広げない」 という旧の懸念も、割り当てで閉じる。
- 割り当て・ログイン記録・許可を同じ通信機の利用期間に結べば、通信機を渡すときに期間を終えるだけで、前のお客様の利用者の条件がまとめて崩れる。割り当てを消し忘れても通らない。

通信機の引き渡し (前のお客様から次のお客様へ) の手順:
1. admin が前の通信機の利用期間を終える (終了時刻を記録)。属する割り当てとサービスの許可を同じ時刻で終え、ログイン記録を消す。消し損ねても、上の条件 (1)〜(4) のどれかを満たさないので通らない。
2. 個別サービスの利用終了処理を行う。
3. 通信機の暗証番号を変える (前のお客様が知っているため)。変更は通信機の設定を扱う担当の手順で行う。照合は通信機が報告した設定と比べるので、新しい暗証番号が効くのは新しい設定が報告された後 。割り当ての条件があるので、変更が効くまでの間も前のお客様は入れない。
4. 新しい通信機の利用期間を始め、次のお客様の利用者を割り当て、サービスの許可を出し。

- サインイン後は「機器単位」と「アカウント単位」を選ぶ。機器単位では、割当確認と機器認証を経て許可されたサービスの一覧へ進む。
- 機器認証は、機器の識別情報と暗証番号を外部の検証インターフェースで照合する。外部データ源と接続先は環境ごとに設定し、検証にはテスト用データを使う。
- 照合前に利用期間と割当の有効性を確認する。成功したら assignment_id に結び付いた 12 時間のログイン記録を作る。
- DynamoDB TTL による削除の時刻に依存せず、API は毎回期限を確認する。
- 暗証番号は保存せず、ログ・監査・エラー応答にも出さない。ブラウザはメモリにだけ保持し、照合後に破棄する。
- 連続失敗を機器単位で制限し、WAF のレート制限と重ねる。初期設定例は 10 分に 5 回失敗で 10 分停止（429）。実際の閾値は負荷試験で決める。
- アカウント画面には複数パスキーの一覧・追加・削除、自分の割当と許可を表示する。admin には招待・停止・再招待、期間・割当・許可の管理、TOTP 登録を提供する。

影響:
- 実装: 台帳のテーブル (core)、admin-users に通信機の利用期間・割り当て・サービスの許可の画面・API、shared レイヤに `require_device` / `require_grant` 相当の確認 (上の条件 (1)〜(4))。
- 運用: お客様が使い始める前に、admin が「招待 → 通信機の利用期間を始める → 割り当て → サービスの許可」を行う。通信機を次のお客様に渡すときは上の引き渡しの手順。
- 利用者: 割り当てられていない通信機には、暗証番号を知っていても入れない (判断 9)。2026-11-05 の改めの後は、access が assigned の通信機のこと (D14)。

### D6. 最初に載せるサービスの SPA の配置

- サインインの後に「通信機単位」と「アカウント単位」を選ぶ。通信機単位は通信機ログイン (暗証番号) を経て、許可されたサービスの一覧に進む。
- アカウント単位で今出すのは、パスキーの管理、割り当てと許可の一覧、admin の管理機能 (判断 1)。

決定 (採用時に確定) 通信機単位:
- 通信機ログインは共通の土台 API が扱う。入力は通信機アカウント 8 桁・製造番号 8 桁・暗証番号 4 桁。手段は「前回値を読み込む」(既定、即時) と「最新値を取得」(通信機と通信する。待機の上限 10 分)。照合は device-backend が、通信機の報告した設定の暗証番号と行う。
- 通信機ログインはサービスに依らない土台の API に移す。サービスの一覧より前に行うため。
- 照合の前に、その通信機アカウントに稼働中の通信機の利用期間があり、利用者がその期間に割り当てられていて、今が割り当ての有効期間内であることを確かめる (D4、判断 9)。
- 改め (2026-11-05): D14 の後は「利用者がその期間に割り当てられていて」を「(2) の根拠 (本人宛の割り当て、グループ宛の割り当て、access が everyone) のどれかがあり」と読む。根拠が無ければ今までどおり device-backend を呼ばない。
- 近道 (2026-11-05 のユーザー決定、): admin でない利用者に見える通信機 (割り当てと everyone を合わせたもの) が 1 台で、その通信機のサービスが 1 つなら、着地 (サインインの直後と、サインイン済みで / を読み込んだとき) で入り方の選択と通信機の一覧を飛ばす。通信機ログインの記録が有効ならサービスへ、無ければその通信機の暗証番号の段へ進む。明示的に開いた通信機の一覧とサービスの一覧は今までどおり出す。条件が崩れれば今までの画面に戻る。目的は操作性で、条件 (1)〜(4) の確かめ方は変えない (DESIGN 2.3)。
- 成功したら台帳にログイン記録を作る。記録は割り当て (通信機の利用期間 × 利用者) に紐づけ (assignment_id とログインの時刻を持つ)、期限は旧と同じ 12 時間。通信機の利用期間か割り当てが終われば、期限内でも効かない。DynamoDB の TTL は削除が遅れるので、読むたびに期限を確かめる 。
- 暗証番号は保存しない。ログ・監査・エラー応答に出さない。画面はメモリだけに持ち、照会に使ったら捨てる。画面を開き直したら入力し直す (旧と同じ)。
- 総当たり対策: 通信機アカウントごとの連続失敗の回数を台帳で数え、例えば 10 分に 5 回失敗したら 10 分止める (429)。数値は旧の案  を初期値にする。WAF のレート制限 (D9) と重ねる。
- 「最新値を取得」の運用中の判定  は画像基盤の台帳を読む。土台の API から画像基盤を引く形は範囲 3 の実装で決める。

決定 (採用時に確定) アカウント単位 (判断 1):
- 今出すもの: パスキーの管理 (複数のパスキーの一覧・追加・本人による削除。D1 の「パスキーの複数登録」)、自分に割り当てられた通信機アカウントと許可されたサービスの一覧。admin には加えて、利用者の管理 (招待・停止・再招待)、通信機の割り当て、サービスの許可、admin 用の TOTP の登録 (D9)。

理由:
- 暗証番号による所有の証明は、旧で dev の実証まで動いている作りで、変える理由が無い。
- アカウント単位で出すサービスがまだ無いので、利用者が自分の状態を確かめられることと、admin の仕事を画面で完結させることを優先する。

影響:
- 実装: 通信機ログインの API (device-backend の呼び出し、ログイン記録、失敗回数) を土台に作る。各サービスの API は、D4 の条件 (1)〜(4) (通信機の利用期間、割り当て、ログイン記録、サービスの許可) を台帳で確かめ直す。
- 運用: device-backend への接続の設定は土台に移る。
- 利用者: 旧と同じ 3 項目で入る。割り当てられた通信機は一覧から選べ、暗証番号だけ入力する。

### D6. サービス SPA の置き方

サービスを別ビルドで配置する場合も、同じ origin・Cognito プールとクライアントを使う。サービスの起動時にはサーバで利用者・割り当て・ログイン記録・サービス許可を確認する。個別サービスの実装は公開範囲に含めない。

### D7. パスキーの RP ID

- ドメインは service-platform.example-cloud.com (dev は service-platform-dev.example-cloud.com)。RP ID がここに固定されるので後から変えない。
- RP ID は各環境のドメイン名そのもの。親ドメインにしない。dev と本番でパスキーは別。

- RP ID は、本番は service-platform.example-cloud.com、dev は service-platform-dev.example-cloud.com (各環境のサイトの FQDN)。親ドメイン example-cloud.com にはしない。
- dev と本番でパスキーは共有できない。プールが別なので、同じ RP ID にしても dev で登録したパスキーは本番の利用者に結び付いていない (推論、確度は高い)。利用者は環境ごとに登録する。
- ローカル開発 (localhost) では、RP ID が localhost でないとブラウザが拒む (推論)。ローカルの独立した PoC では RP ID を localhost にする。

理由:
- RP ID は環境ごとの FQDN に限定し、他のサイトとの信頼範囲を分ける。
- 共有の利点 (dev と本番で同じパスキー) はプールが別なので得られない。
- RP ID を変えると全員が登録し直しになる。公開前に決める。

影響:

- 構成要件: core テンプレートの `WebAuthnRelyingPartyID` を環境のドメインにする (63 文字以内に収まる)。
- 運用: dev で試す社員は dev 用にもパスキーを登録する。
- 利用者: 影響なし (本番だけを使う)。

### D8. admin が利用者のパスキーを消す手段

- admin が他人のパスキーを消す API は無いので、本人が消す。盗難のときは、無効化 → 全セッション失効 → 削除 → 再招待とし、user_id は保つ (判断 5)。

- admin が他人のパスキーを一覧・削除する API は無い (調査ノート Q3)。admin に分かるのは、パスキーを 1 つ以上持つか (AdminGetUserAuthFactors の WEB_AUTHN) まで。
- 代わりの手順を 4 つ用意する。普段は手順 1 と 2 を使い、手順 3 は一時的な措置、手順 4 は受信箱の乗っ取りの疑いのときに使う。

| 手順 | 場面 | 操作 | 結果と注意 |
| --- | --- | --- | --- |
| 1 本人が消す | 端末を替えた、古いパスキーを整理したい | 本人がアカウントの画面で一覧 → 削除 (`deleteWebAuthnCredential`) | 正規の方法。本人がサインインできること (別の端末のパスキー、またはメールのコード)。端末ごとに登録していれば、残った端末で入って消せる (D1 の「パスキーの複数登録」) |
| 2 無効化 → 再招待 | パスキーの盗難・乗っ取りの疑い、本人がサインインできない、admin が TOTP を失くした  | admin が台帳で停止 → AdminDisableUser → AdminUserGlobalSignOut → AdminDeleteUser → AdminCreateUser で再招待 → 新しい sub を同じ user_id に結ぶ → 下の「再招待の後の復帰」を経て台帳を有効に戻す | パスキーも、後から足されたパスワード (D1) も消える (PoC 8)。user_id・割り当て・履歴は残る。有効に戻すまで台帳は停止のまま (呼べるのは D9 の例外の API だけ)。復帰の条件は admin とそれ以外で違う (下の表) |
| 3 全セッションの失効だけ | 端末を一時的に失くした (見つかる見込みがある) | admin が台帳で停止 → AdminUserGlobalSignOut | パスキーと、後から足されたパスワード (D1) は残る。再び使えるようにすると、同じパスキーがまた使える。見つからなければ手順 2 へ |
| 4 受信箱の乗っ取りの疑い | お客様のメールが他人に読まれている (メールのコードで入れるので、他人がサインインし、その人のパスキーを足せる) | 下の「受信箱が侵害されたときの回復」 | 同じメールアドレスへそのまま再招待しない (攻撃者もメールのコードで入り直せる) |

- 無効化 (AdminDisableUser) だけではパスキーは消えない (推論)。再び有効にすると同じパスキーが使えるので、盗難のときは必ず削除して再招待する。
- AdminUserGlobalSignOut の後も、発行済みのトークンは期限まで JWT authorizer を通る (推論)。台帳の停止を全 API が確かめるので、SERVICE-PLATFORM の API はすぐ止まる (D3。例外は D9 の「停止中でも呼べる API」の 2 つだけ)。
- パスキーの追加・削除とパスワードの後付けは、画面 (Amplify) が Cognito を直接呼ぶので SERVICE-PLATFORM の監査テーブルに残らない (D12)。盗難や乗っ取りを調べるとき、監査テーブルだけでは「いつ誰のパスキーが足されたか」は分からないので、アカウントの CloudTrail を sub で引く (D12、PoC 13)。admin の画面で分かるのは、パスキーを 1 つ以上持つか (と、`PASSWORD` を使えるか) までである。乗っ取りの間に足されたものは、手順 2 / 4 の削除で消える (PoC 8)。
- admin の回復で「TOTP の解除だけ」は使わず、手順 2 にする。TOTP を外すと、TOTP の間に登録したパスキーとメールのコードで入れるようになる (PoC 11)。TOTP の現在状態は AdminGetUser の UserMFASettingList で見る。AdminGetUserAuthFactors の `ConfiguredUserAuthFactors` は、TOTP を外しても `SOFTWARE_TOKEN` を残し、使えない要素も出す (PoC 5 / 11)。

再招待の後の復帰 (手順 2 と手順 4 で共通。利用者の種別で分ける):
- 順序は 停止 → 再招待 → 本人の登録 → 別経路の確認 → 有効。台帳は再招待の後も「停止」のままで、有効に戻すまで SERVICE-PLATFORM の API は 403 になる。例外は D9 の「停止中でも呼べる API」の 2 つ (admin の「TOTP の登録を終えた」API と、自分の状態を読む API) だけ。
- admin でない利用者は、2 と 3 の順を問わない (手順 4 では 3 を再招待より前に行う)。admin は 2 の後に 3 を行う (登録の時刻を確かめるため)。

| 段 | admin でない利用者 (お客様・社員) | admin |
| --- | --- | --- |
| 1 停止と再招待 | 手順 2 (手順 4 なら下の 1〜5)。招待はパスワード無し (メールのコード) | 手順 2 と同じく停止 → 削除 → 作成。作成は admin の招待と同じく、招待メールを送らず (`MessageAction=SUPPRESS`)、一時パスワードを別経路で渡す。admin グループに付け直し、台帳の `mfa_enabled_at` を消し、admin の状態を「準備中」に戻す (前の「有効」は引き継がない) |
| 2 本人の登録 | 本人が新しい招待のメールのコードでサインインし、新しい端末でパスキーを登録する。画面が Cognito を直接呼ぶので、SERVICE-PLATFORM の API は通らない | 本人が一時パスワードでサインインし、本パスワードを決め、TOTP を登録して「TOTP の登録を終えた」API を呼ぶ (D9 の例外 1)。admin の状態は「確認待ち」になる。パスキーの登録は求めない (admin は有効化後に任意でパスキーを登録できる。パスワード + TOTP の入口も残る。D9、判断 20) |
| 3 別経路の確認 | admin が、招待のときに台帳に控えた連絡先 (組織の窓口の電話など) で、本人と組織の窓口に確かめる。メールでの申し出だけでは戻さない。パスキーの登録は AdminGetUserAuthFactors の `WEB_AUTHN` で確かめる | 本人以外の admin (使える admin がいなければ IAM の権限を持つ運用者が scripts で) が、別経路で本人を確かめ、登録の時刻 (`mfa_enabled_at`) が本人の操作と合うことを確かめる |
| 4 有効に戻す | admin が台帳を「有効」に戻す。手順 4 では、受信箱の安全確認 (または宛先の変更) が済んでいることも条件にする | 確かめた admin が 1 つの操作で、利用者の台帳を「有効」に戻し、admin の状態を「有効」にする (D9 の「有効にする」)。本人がパスワード + TOTP でサインインし直すと、admin の操作が通る |
| 監査 | 確かめた人・方法・日時と、戻した操作を残す (D12) | 同左 |

受信箱が侵害されたときの回復 (手順 4):
1. 止める: admin が台帳で停止 → AdminDisableUser → AdminUserGlobalSignOut。
2. 別経路で本人を確かめる: 招待のときに台帳に控えた連絡先 (組織の窓口の電話など) へ admin から連絡し、本人と組織の窓口に確かめる。メールでの申し出だけでは回復しない。確かめた人・方法・日時を監査に残す。
3. 受信箱の安全を確かめる: 本人 (または組織の窓口) が、メールのパスワードの変更と、転送や自動振り分けの設定の確認を済ませたことを確かめる。安全にできないときは、別のメールアドレスにする。
4. 宛先を変える (必要なとき): 再招待のときに新しいメールアドレスで作る。user_id は保つ。
5. 再招待: 手順 2 と同じく削除 → 作成 → 新しい sub を同じ user_id に結ぶ。台帳は停止のまま。乗っ取りの間に足されたパスキーとパスワードは、削除で消える (PoC 8)。
6. 台帳を有効に戻す: 上の「再招待の後の復帰」による。admin でない利用者では、この手順の 2 が、その「3 別経路の確認」に当たる。admin では、この手順の 2 (再招待の前の本人確認) に加えて、TOTP の登録の後に別の admin が別経路で本人を確かめ、登録の時刻 (`mfa_enabled_at`) を照合して有効にする (共通の表の admin の列のとおり。D9 の「有効にする」)。どちらも、加えて 3 (または 4) が済んでいること。戻すまでは、Cognito でサインインできても、SERVICE-PLATFORM の API は D9 の例外の 2 つを除いて 403 になる。

影響:

- 構成要件: admin-users に「停止」「再招待」(削除・作成・引き当ての付け替えを 1 操作に) を設ける。アカウントの画面にパスキーの一覧・追加・削除 (D1)。台帳に連絡先。
- 運用: 盗難の連絡を受けたら手順 2。受信箱の乗っ取りが疑われるときは手順 4 (別経路の本人確認と受信箱の安全確認を、再招待より先に行う)。
- 利用者: 再招待のメールが届いたら、初回と同じ手順で入り直す。admin には招待メールは届かず、一時パスワードを別経路で受け取る。

### D9. admin 操作の追加検証

- admin は TOTP を必須にする。admin を有効にするのは、別の admin が別経路で本人を確かめた後 (判断 8)。
- admin はパスワード + TOTP、または登録済みの本人確認つきのパスキーでサインインする。どちらも強い入口として認める (2026-11-06 のユーザー決定、判断 20)。


| 守り | 内容 |
| --- | --- |
| admin の認証要素 | TOTP を必須・優先のまま維持する。プールの `WebAuthnFactorConfiguration: MULTI_FACTOR_WITH_USER_VERIFICATION` と利用者ごとの `WebAuthnMfaSettings.Enabled=true` により、本人確認つきのパスキーが第一要素として MFA を満たす。パスワードの入口では TOTP を求め、パスキーをその第二要素には使わない (判断 8 / 20) |
| 現在状態の確認 | admin の API は毎回 Cognito の現在状態を確かめている (admin-users、既存)。ここで AdminGetUser の UserMFASettingList に `SOFTWARE_TOKEN_MFA` があることも確かめる (`ConfiguredUserAuthFactors` では見ない。判断 13)。有効でない、admin グループに無い、TOTP が無い、のどれかなら 403 (fail-closed) |
| セッションの確認 | 設定の確認だけでは足りない。UserMFASettingList は今の設定で、提示されたトークンのサインイン方法は示さない。admin の API は、登録前のセッションを除外し、登録後の強い入口からのサインインを受け付ける (判断 20)。方式は (b) に決めた (下記。判断 12) |
| レート制限 | WAF の web ACL を 2 つ。CloudFront (us-east-1 で作る) に IP ごとのレートベース ルール、ユーザープール (東京) に公開 API (InitiateAuth など) へのレートベース ルール。HTTP API には WAF を直接付けられないので CloudFront で受ける。加えて HTTP API のステージ・ルートのスロットリング、暗証番号の失敗回数 (D5)。公開用テンプレートでは超過要求を Block する。パスキーの取り消し 1 回につき候補照会で InitiateAuth が 2 回になる。閾値の設計に織り込む。ユーザープールの web ACL には、ChangePassword を最初から Block するルールも置く (D1、判断 15) |
| 直叩き | `x-origin-verify`  で CloudFront を通らない要求を 403 にする |
| 監査 | admin の操作は全件、user_id で記録する (D12)。admin-users の構造化ログ (既存、365 日) も続ける |
| dev | dev を立てる時点で、最初の admin の手順 (下記) で TOTP まで済ませる 。dev も社外から届くため |

admin のセッションを登録時刻で確かめる方式 (判断 12 / 20):

| 方式 | 扱い | admin の API が通す条件 |
| --- | --- | --- |
| (b) 台帳の `mfa_enabled_at` | 決定 | 台帳の admin の状態が「有効」で、トークンの `auth_time` (サインインした時刻) が `mfa_enabled_at` より後。`auth_time` は更新では変わらない (公式、PoC 10) ので、TOTP を登録する前にサインインしたセッションを更新しても通らない。`iat` (発行時刻) は更新のたびに新しくなるので、`iat` だけでは比べない |
| (a) `acr` / `amr` | 将来。PoC 6 の対象プールでは得られなかった (`TARGET_ACR_VALUES` は無視され、トークンに `acr` / `amr` が無い)。提供が来たら試し直す | ID トークンの `acr` が `urn:cognito:loa:4` (既定値。パスワード + TOTP) で、`amr` に `otp` と `mfa` がある。`acr` が無い、または低いトークンは 403。公式は段階的に提供中とする (Essentials 以上)。パスワードだけは `loa:1`、メールのコードだけは `loa:2`、パスキーは `loa:3`。更新しても `acr` / `amr` は引き継がれる (公式)。Amplify 6.20 は `TARGET_ACR_VALUES` を渡せないので、SDK を直接呼ぶ |

admin の状態の管理 (admin の API は台帳の admin の状態が「有効」でなければ 403。状態は 準備中 → 確認待ち → 有効、再招待すると 準備中 から):

| 場面 | 操作 | 結果 |
| --- | --- | --- |
| admin にする | admin (最初の 1 人は下の scripts) が admin グループに入れる。台帳の admin の状態は「準備中」、`mfa_enabled_at` は無し。admin の招待では招待メールを送らず (AdminCreateUser の `MessageAction=SUPPRESS`)、一時パスワードを別経路で渡す | admin の API は 403。アカウントの画面の TOTP の登録だけ使える (下の例外 1) |
| TOTP を登録する | 本人がアカウントの画面で登録 (Amplify の `setUpTOTP` → `verifyTOTPSetup` → `updateMFAPreference`) → 画面が「登録を終えた」API を呼ぶ → サーバが AdminGetUser で `SOFTWARE_TOKEN_MFA` を確かめ、AdminUserGlobalSignOut で全セッションを失効させ、失効後の時刻を `mfa_enabled_at` に書き、状態を「確認待ち」にする | まだ 403。本人はパスワード + TOTP でサインインし直して待つ |
| 有効にする | 本人以外の admin (最初の admin と緊急時は IAM の権限を持つ運用者が scripts で) が、別経路 (電話や対面) で、本人が登録したこと (登録の時刻 = `mfa_enabled_at` が本人の操作と合うこと) を確かめてから、状態を「有効」にする。再招待の後は、同じ操作で利用者の台帳も「有効」に戻す。確かめた人・方法・日時を監査に残す | ここから admin の操作が通る (下の「停止を解く条件」) |
| TOTP を失くした (紛失など) | 「TOTP の解除だけ」は使わない。本人以外の admin が、下の「再招待する」(D8 手順 2) を行う | 前のパスワード、TOTP、パスキーは利用者ごと消える (PoC 8)。前のトークンは、古い sub の行の無効の印で 403 になる |
| 再招待する (盗難、TOTP の紛失など。D8 手順 2 / 4) | 削除・作成し、admin グループに付け直し、`mfa_enabled_at` を消し、状態を「準備中」に戻す。一時パスワードは別経路で渡す。利用者の台帳は「停止」のまま | 前の「有効」は引き継がない。本人は下の例外 1 で「TOTP を登録する」まで進める。「有効にする」で、利用者の台帳と admin の状態を一緒に「有効」に戻す (D8 の「再招待の後の復帰」の admin の列) |
| TOTP を登録し直す | 本人が一時パスワードでサインインし、本パスワードを決め、TOTP を登録する。状態は「確認待ち」になり、上の「有効にする」を経て「有効」に戻る | 登録の前に得たセッションは、`auth_time` が新しい `mfa_enabled_at` より前なので 403 |
| 停止を解く条件 | 状態が「有効」(本人以外が別経路で確かめた)、TOTP が設定済み、`mfa_enabled_at` より後にパスワード + TOTP または本人確認つきのパスキーでサインインしたトークン、の全部 | 条件を満たした要求から admin の操作が通る |

停止中でも呼べる API (利用者の台帳が「停止」のときと、admin の状態が「準備中」のときの例外は、この 2 つだけ。ほかの API はすべて 403):

| API | 呼べる人 | すること |
| --- | --- | --- |
| 例外 1: TOTP の登録を終えた | admin グループに属し、admin の状態が「準備中」の本人。利用者の台帳が「停止」でもよい | 本人のトークンで呼ぶ。サーバは Cognito の現在の状態 (有効、admin グループ、`SOFTWARE_TOKEN_MFA`) を確かめ、全セッションを失効させてから、自分の台帳の行に `mfa_enabled_at` を書き、admin の状態を「確認待ち」にする (上の「TOTP を登録する」)。ほかの行は書かない |
| 例外 2: 自分の状態を読む | サインインした本人 (状態を問わない) | 自分の台帳の状態 (有効 / 停止) と admin の状態を返す。画面が「停止中」「確認待ち」などを出すため。ほかの利用者のことは返さない |

- 再招待の前のトークンは使えない。再招待で古い sub の行に無効の印を付ける (D3) ので、古いトークンでは例外 1 も例外 2 も user_id を引けず 403 になる。
- admin でない利用者の復帰 (D8) では、SERVICE-PLATFORM の API を呼ばない (パスキーの登録は画面が Cognito を直接呼ぶ)。

最初の admin の作り方 (dev と本番の初回の起動も同じ):
1. IAM の権限を持つ運用者 (AWS の資格情報で scripts を流せる人) が、管理者作成用の運用ツールを流す。スクリプトは、(1) AdminCreateUser (一時パスワード、`email_verified=true`、招待メールは送らない `MessageAction=SUPPRESS`)、(2) 台帳に利用者の行と sub の引き当てを書く (user_id を採番)、(3) admin グループに入れ、台帳の admin の状態を「準備中」にする、(4) 監査に「scripts による作成」と実行した IAM の主体を残す。一時パスワードは別経路で本人に渡す。
2. 本人は一時パスワードでサインインし、本パスワードを決め、アカウントの画面で TOTP を登録する (上の表)。状態は「確認待ち」になる。
3. 運用者が別経路で本人の登録を確かめ、scripts で状態を「有効」にする (監査に残す)。本人がパスワード + TOTP でサインインし直すと、admin の操作が通る。
4. 2 人目からは、この admin が画面から招待し、「有効にする」もこの admin が行う。

全ての admin が TOTP を失くした (または使える admin がいない) ときの緊急の復旧:
1. IAM の権限を持つ運用者が、対象の admin が本人であることを社内の別経路で確かめる。
2. 緊急用の scripts で、対象の admin を再招待する (D8 手順 2。TOTP の解除だけは使わない。判断 13)。台帳で停止 → AdminDisableUser → AdminUserGlobalSignOut → AdminDeleteUser → AdminCreateUser (一時パスワード、`MessageAction=SUPPRESS`) → 新しい sub を同じ user_id に結ぶ (古い sub の行に無効の印) → admin グループに付け直す → `mfa_enabled_at` を消し、admin の状態を「準備中」に戻す。一時パスワードは社内の別経路で渡す。
3. 監査に残す (実行した IAM の主体、対象、理由)。Cognito の管理 API の呼び出しは、アカウント既存の CloudTrail にも残る 。
4. 本人が一時パスワードでサインインし、本パスワードを決め、TOTP を登録し直す (「確認待ち」)。
5. 運用者が別経路で本人の登録を確かめ、scripts で利用者の台帳と admin の状態を「有効」にする (監査に残す)。本人がサインインし直す。
- scripts を流す IAM の権限は、運用者だけに持たせる。

- TOTP の登録画面は準備中の admin にだけ出す (Amplify の `setUpTOTP` → `verifyTOTPSetup` → `updateMFAPreference`、続いて登録完了 API)。有効な admin にパスキーの管理を出す。確認待ちには登録操作を出さない。
- パスキーだけを admin の条件にする案は採らない。パスキーはサインインさえできれば誰でも足せる (`associateWebAuthnCredential` はサインイン済みだけが条件)。パスワードやメールだけで入れる admin は、入った後で自分のパスキーを足せる。admin の入口の強さは、いちばん弱い入口で決まる。
- 判断 20 で passkey MFA を採用した。プールの設定と利用者ごとの有効化を組み合わせ、TOTP を持つ admin も本人確認つきのパスキーで入れる。PoC 5 は passkey MFA を有効にする前の結果として残す。dev での組み合わせの実測は PoC 15 に記す。
- 料金: web ACL 1 つ月 5 USD、ルール 1 本月 1 USD、要求 100 万件 0.60 USD。2 つの web ACL にレート制限のルール 1 本ずつと、ユーザープール側に ChangePassword のルール 1 本 (判断 15) で、月 13 USD + 要求の料金 (調査ノート Q8、AWS Pricing MCP)。

理由:

- threat protection (Plus) はレート制限をせず、公式に WAF を使うよう書かれている (参考資料)。

影響:

- 構成要件: admin-users の現在状態の確認に TOTP の確認と、セッションの確認 ((b)) を設ける。台帳に admin の状態と `mfa_enabled_at`。「TOTP の登録を終えた」(停止中でも呼べる例外 1)「自分の状態を読む」(例外 2)「admin を有効にする」(別経路の確認の記録つき。再招待の後は利用者の台帳も戻す) の API。admin のパスワードの変更 (別の admin の AdminSetUserPassword。D1)。WAF の web ACL 2 つ (edge と core。core に ChangePassword の Block)。HTTP API のスロットリング。アカウントの画面に TOTP の登録 (admin のみ)。管理者作成用の運用ツールを用意し (招待・台帳・グループ・監査。招待を管理者に限定する)、緊急の復旧用のスクリプトを設ける。
- 運用: admin を増やす手順は「一時パスワードで招待 (招待メールは送らず別経路で渡す) → 本パスワード → admin グループ (準備中) → 本人が TOTP を登録 (確認待ち) → 別の admin が別経路で確かめて有効にする → サインインし直す」。TOTP を失くした admin は、別の admin が再招待し (D8 手順 2。一時パスワードは別経路で渡す)、本人が登録し直し、別の admin が確かめて有効に戻す。使える admin がいなければ緊急の復旧。
- 利用者: お客様には影響なし。

### D10. 通知元と添付領域の境界

通知キューの送信権限をアプリの IAM ロールに限定し、アプリに対応する添付プレフィックスを扱う。宛先ドメインの制限は通知用途に合わせて明示する。トークン・暗証番号・認証情報を通知本文やログへ入れない。

### D11. 既存の利用者の移行

新しい認証基盤へ招待し、本人の認証要素を登録する。業務上の利用者・組織の対応を確認してから、グループ、通信機の利用期間、割り当て、サービス許可を作る。認証情報とログイン記録はコピーしない。グループと access は移行前に設計へ組み込む (判断 19)。

### D12. 監査

- 誰が・いつ・どの通信機に・どのサービスで・何をしたかを、user_id で残す。請求の実績の基礎にする。
- 記録の項目: user_id、そのときの email (読むための控え)、役割、操作、サービス、通信機アカウント、通信機の利用期間 device_period_id、割り当て assignment_id、結果、送信元 IP、user_agent、時刻 (UTC)。暗証番号・トークン・本文 (現場名、宛先など) は記録しない 。
- 記録する操作: サインインの後の通信機ログインの成否、admin の操作 (招待・停止・再招待・台帳を有効に戻す操作・別経路の本人確認・email の変更・通信機の利用期間・割り当て・サービスの許可・TOTP の登録・admin のパスワードの変更 (一時パスワードの発行)・admin を有効にする操作・scripts による作成と緊急の復旧)、各サービスの重要な操作 。
- パスキーの追加・削除 (と D1 のパスワードの後付け): 画面 (Amplify) が Cognito を直接呼ぶ (StartWebAuthnRegistration / CompleteWebAuthnRegistration / DeleteWebAuthnCredential、ChangePassword)。SERVICE-PLATFORM の API を通らないので、監査テーブルには残らない。追う手段はアカウントの CloudTrail にする (判断 16)。
  - 4 つの呼び出しは管理イベントとして記録され、`additionalEventData.sub` で利用者が分かる。トークンとパスワードは隠される。DeleteWebAuthnCredential には credentialId が残り、登録には残らない。プールの ID はイベントに無いので、sub で引く (PoC 13)。
  - sub から user_id を引くため、再招待で古い sub の行を消さず、無効の印を付けて残す (D3)。
  - イベント履歴 (lookup-events) は 90 日まで。長く残すにはアカウントの証跡に頼る 。WAF で止めた要求は、PoC の検索の時点と時間窓では検出しなかった。止めた記録は WAF のログで見る。
  - 画面が成功の後に SERVICE-PLATFORM の API へ知らせて監査に書く案は作らない。最善努力で欠けるうえ、CloudTrail で追えるため。
- 追記だけの仕組み: IAM で絞れるのは操作の種類 (`PutItem`) までで、`PutItem` は同じキーの既存の行を置き換えられる。そのため `audit.emit` は `ConditionExpression: attribute_not_exists(PK)` を付け、SK に推測できない ID (ULID) を入れて、既存の行を上書きさせない。
- 保持: 操作の記録は 365 日 (TTL)。請求の実績の基礎になる記録 (通信機の利用期間の開始・終了、サービスの許可の開始・終了、割り当ての変更) は期限を付けない 。

理由:

- 監査を台帳とは別のテーブルにするのは、台帳を読み取り専用に保ちつつ、全サービスが監査を残せるようにするため。

影響:

- 構成要件: core に監査テーブルを足し、名前を SSM で公開する。shared レイヤに監査の書き込み (`audit.emit` 相当。監査テーブルへの `PutItem` だけ) を置き、全 API から呼ぶ。監査の閲覧には管理者権限を要求する。
- 運用: 集計を再構築できるよう、請求の根拠となる記録を保持する。
- 利用者: なし。

### D13. グループと割り当ての相手 (2026-11-05 追記)

決定 (ユーザー決定、2026-11-05):
- グループは台帳の実体として持つ。木は 3 段まで。
- 段の名前は固定しない。例として「会社 > 部署 > 課」「県 > 事務所 > 出張所」「コンサル > 支店」を見せるだけで、名前は登録者 (admin) が自由に付ける。
- 人は複数のグループに属せる。所属の行に親までの経路を持たせ、判定を軽くする。
- 割り当ての相手は人かグループ。既存の人単位の割り当ては、そのまま有効。
- 本番の移行 (旧の台帳の写し) の前に入れる (判断 19)。

設計 (。2026-11-05 の設計判断で確定):
- 呼び名: 台帳のグループ (以下、グループ) は人の集まりの木である。Cognito の admin グループ (D4 の役割の正本) とも、割り当ての行の役割の列 (`role`。判断 2) とも別のもの。文書と画面では「グループ」と書く。
- グループの項目: group_id (ULID)、名前 (1〜100 文字)、親の group_id (根は無し)、経路 (根から自分までの group_id の並び)、段 (1〜3)、状態 (稼働中 / 終了)、メモ、作った人と日時、version。段の名前の列は持たない。
- 作る: 親の段が 3 なら子を作れない。同じ親の下 (根どうしを含む) の稼働中のグループと同じ名前は付けない。どちらも 409。
- 名前を変える: できる。経路は ID の並びなので、所属の行は書き換えない。
- 付け替え (親を変える) は作らない。経路の写しを持つ所属の行を書き換えることになるため。組み替えは、新しいグループを作って所属と割り当てを移し、古いグループを終える。
- 終える: 稼働中の子のグループ、所属、終わっていない割り当てが 1 つも無いときだけ (409 `GROUP_IN_USE`)。行は消さず、状態を終了にする。これで「所属の経路にあるグループはどれも稼働中」が常に成り立ち、条件 (2) はグループの行を読まずに済む。
- 所属: 利用者 × グループ。行に、所属の ID (membership_id。ULID)、根から属するグループまでの経路の写し、属した時刻 (added_at) を持つ。所属の ID は使い回さない。外して付け直せば新しい ID になり、条件 (3) はこの ID で前の所属と見分ける (D14)。added_at は表示と監査のためで、照合に使わない。期間は持たない (期間は割り当てが持つ)。外すときは行を消し、履歴は監査に残す。同じ人が親と子の両方に属してもよい。停止中の利用者も属させられる (通信機の利用は停止で止まる。割り当てと同じ)。
- グループ宛の割り当ては、そのグループと、その下の段のグループに属する人に効く。人の所属の経路に割り当てのグループが含まれていれば効く。
- グループ宛の割り当ての項目は人宛と同じ (assignment_id、valid_from / valid_to、役割、割り当てた人) に、相手の型 (`target_type` = `group`) と group_id を足す。同じグループへの、有効期間が重なる割り当ては作れない (人宛と同じ規則)。同じ人に人宛とグループ宛の両方が効いてもよい。既存の人宛の行は相手の型を持たず、無いときは人宛と読む (書き換えない)。
- 製造番号の控え: 人宛の割り当ては今までどおり割り当ての行に持つ。グループ宛の割り当ては行を複数の人が共有し、everyone (D14) には行が無いので、本人の行に控える。製造番号は人ごとに初回の通信機ログインで 1 回入れる (ほかの人が入れた製造番号を見せない)。
- 作るのは弊社 admin だけ (判断 2 の A のまま)。グループごとの管理者は置かない (将来の候補は判断 17)。
- 書き込みの守り: グループの作成・名前の変更・終了、所属の追加・外す、グループ宛の割り当ての追加・終了は、今の admin の操作と同じく、書き込みのトランザクションに呼び出し元の検査 (D9。台帳の有効な admin で、同じ sub) を入れる。要求の初めの確かめだけに頼らない (要求の後に止められた admin の変更を確定させない)。操作ごとの中身は admin-users の設計書。

台帳の項目の案 (キーは  で確定する。DESIGN.md 11.1):

| データ | PK | SK | 主な項目 |
| --- | --- | --- | --- |
| グループ | `GROUP#{group_id}` | `PROFILE` | group_id、名前、親の group_id、経路、段、状態、メモ、作った人・終えた人と日時、version |
| 子のグループの控え | `GROUP#{親の group_id}` (根は `GROUP#ROOT`) | `CHILD#{group_id}` | 状態と名前の写し。作るときの名前の重なりと、終えるときの「稼働中の子が無い」の確かめに使う |
| 根の直列化 | `GROUP#ROOT` | `META` | version。根どうしの名前の重なりを、親の version と同じ仕組みで守る (根の CHILD の控えもこの PK の下) |
| 所属 | `USER#{user_id}` | `MEMBER#{group_id}` | membership_id、経路の写し、added_at、属させた人 |
| 所属の逆引き | `GROUP#{group_id}` | `MEMBER#{user_id}` | membership_id、added_at、属させた人。所属と同じトランザクションで書く |
| グループ宛の割り当て | `DPERIOD#{device_period_id}` | `GROUP#{group_id}#{assignment_id}` | 人宛の割り当てと同じ項目 + `target_type`・group_id。製造番号は持たない |
| グループ宛の割り当ての逆引き | `GROUP#{group_id}` | `ASSIGN#{device_period_id}#{assignment_id}` | 通信機アカウント、有効期間、組織名の写し |
| 製造番号の控え | `USER#{user_id}` | `SERIAL#{device_period_id}` | 通信機アカウント、製造番号、控えた日時。グループ宛と everyone のログインで書く |

理由:
- 人単位だけでは、会社や部署の人数分の割り当てを通信機ごとに作ることになり、人の出入りのたびに全部の通信機を直す。グループに割り当てれば、人の出入りは所属の 1 行で済む。
- 経路を所属の行に写せば、(2) の確かめは「本人の所属の Query 1 回」と「P のグループ宛の割り当ての Query 1 回」で済み、木をたどらない。付け替えと、使っているグループの終了を作らないので、写しが古くならない。
- 段の名前を固定しないのは、お客様ごとに組織の形が違うため (ユーザー決定)。段の数 (3) だけを決めれば、判定は名前に依らない。

影響:
- 実装 : 台帳の行 (上の表)。admin-users にグループと所属の API・画面、割り当ての相手の型。shared の access の条件 (2)。base の通信機の一覧と製造番号の控え。
- 運用: 本番の移行で旧の利用者を写すときは、先にグループを作り、人を属させてから割り当てる (人単位で写してから作り直さない。判断 19)。
- 利用者: 動線は変わらない。通信機ログインの一覧に、グループ経由で割り当てられた通信機も出る。

### D14. 通信機の利用期間の access (everyone / assigned) (2026-11-05 追記)

決定 (ユーザー決定、2026-11-05):
- 通信機の利用期間に属性 access を持つ。値は everyone (誰でも) と assigned (割り当てだけ)。既定は everyone。
- everyone は「サインインした人なら誰でも」の意味。通信機ログインの一覧に出て、門は通信機ログインの暗証番号。ほかのお客様の利用者が一覧で見ても、暗証番号を通れないので、そこまで固くしない。「持ち主の組織の全員」の意味ではない (判断 18)。
- everyone は「どちらでもできるようにするための保険」。everyone と assigned の両方を持ち、既定を everyone にして、割り当てが無くても使える状態を保つ。assigned は必要な通信機だけに使う。
- 将来の機器単位の接続 (LTE-M など。通信機ログインが無い) では、人やグループの割り当てが門になる。だから割り当ての仕組み (人 | グループ) は everyone と並んで要る。今回は設計で触れるだけで、実装の範囲に入れない。
- 条件 (3) 通信機ログインと (4) サービスの許可は変えない (どちらも要ることは変わらない)。
- 本番の移行の前に入れる 。既存の利用期間は、属性が無ければ everyone として扱う。

設計 (。2026-11-05 の設計判断で確定):
- 条件 (2) を「利用者が P を扱う根拠がある」に広げる。根拠は次の 3 つ。どれも台帳の有効な利用者 (D3) であることが前提。根拠ごとに、使い回さない ID (世代) を持つ。
  - (a) 本人宛の割り当て: P に属し、今が有効期間内。ID は assignment_id。
  - (b) グループ宛の割り当て: P に属し、今が有効期間内で、そのグループが本人の所属の経路に含まれる。ID は assignment_id と、そのグループを経路に含む所属の membership_id (D13。複数あれば全部)。
  - (c) everyone: P の access が everyone (属性が無いときを含む)。ID は P の access の世代 (access_gen)。everyone で始めるときと、assigned から everyone に切り替えるたびに、新しい ULID を振る。属性の無い既存の行は、started_at から作る決まった値 (`START#{started_at}`) を世代として読む (読み取りで行に書き足さない)。
  - access が assigned なら (a)(b) だけを見る。根拠が 1 つも無ければ、今までどおり 403 `DEVICE_NOT_ASSIGNED` ((1) と区別しない)。
- 条件 (3) を根拠で書き直す。ログイン記録に根拠の種類 (`basis` = user / group / everyone) と ID (user と group は assignment_id、group はさらに membership_ids、everyone は access_gen) を持たせる。通すのは、記録が P に属し (同じ device_period_id)、期限内 (12 時間) で、記録の根拠が今の (2) の根拠の集合に含まれるときだけ。含まれるとは、user なら同じ assignment_id の (a) があること、group なら同じ assignment_id の (b) があり、その (b) を作る所属の membership_id のどれかが記録の membership_ids にあること、everyone なら (c) があり、世代が同じこと。
- 時刻 (秒) は比べない。台帳の時刻は秒単位なので、同じ秒の失効と再付与 (割り当ての終了と新しい割り当て、所属を外して付け直す、everyone → assigned → everyone) を時刻では見分けられない。ID は使い回さないので、前の記録は同じ秒でも通らない。今の (3) (同じ割り当てで valid_from 以後) は根拠 (a) のときの形で、意味は変わらない (記録は書き込みの条件でその割り当ての有効期間の中にしか書けないので、ID が同じなら時刻の比較は要らない)。
- 複数の所属: 記録の membership_ids には、ログインの時にその割り当てのグループを経路に含んでいた所属を全部入れる。そのどれかが残っている限り権限は途切れていないので、記録は続く (1 つを外しても、ほかの所属で続く)。ログインの後に足した所属だけが残った場合は入り直しになる (途切れたかどうかを記録から確かめられないので、安全な側に倒す)。
- 通信機ログインが記録する根拠は (a) → (b) → (c) の順で 1 つ選ぶ (同じ型の中では assignment_id の大きいもの、つまり後に作ったもの)。割り当てがあれば割り当てを根拠にするので、access を assigned に変えても割り当てのある人のログインは続き、監査に assignment_id が残る。
- ログイン記録の置き換え: 通信機ログインは、初めに本人のログイン記録を強い整合で読み、書くときはその版 (last_op_id。無ければ「行が無いこと」) を条件にして置き換える。根拠の始まりの大小では縛らない。前の根拠が無くなった後の、別の有効な根拠への入り直しはいつでもできる。同じ利用者の並行するログインは、片方だけが書けて、もう片方は 409 `CONFLICT` になる。書くトランザクションには、選んだ根拠の行 (割り当て、所属、P) の条件を入れ、書いた時点で根拠があることを守る。
- (3) は「(2) の根拠の集合」と比べるので、割り当てを足しても、記録の根拠が残っている限りログイン中の人は入り直さなくてよい。根拠が無くなった記録だけが落ちる。
- access の変更は admin だけ。変更で P の version を上げ、変えた時刻と人を書く (稼働中の指しにも写す)。everyone にするときは新しい世代を振る。everyone → assigned では、割り当ての無い人は (2) で、everyone を根拠にした記録は (3) で落ちる。ログイン記録は探して消さない (誰が everyone でログインしたかを P から引けないため。消し損ねても通らない、は D4 と同じ考え)。everyone → assigned → everyone と戻しても、世代が替わるので、前の everyone の記録は (同じ秒の切り替えでも) 落ちる。
- 所属を外したときも、ログイン記録は消さない。記録の membership_ids が今の所属に 1 つも無くなれば (3) で落ちる。外して付け直しても新しい membership_id になるので、前の記録は落ちる。
- 書き込みの守り: access の変更と、access を選ぶ利用期間の開始は、今の admin の操作と同じく、書き込みのトランザクションに呼び出し元の検査 (D9) を入れる (D13 の「書き込みの守り」と同じ)。
- 一覧: everyone の通信機は、稼働中の利用期間の指し (`DEVICE#{account}` / `CURRENT`) に access と、変えた時刻と人 (access_changed_at / access_changed_by) を写し、GSI1 の一覧 (結果整合) から出す。属性の無い既存の行は、access を everyone、変えた時刻を started_at、変えた人を空 (null) として返す。一覧は表示だけに使い、通信機ログインは強い整合の (1)〜(3) で確かめ直す (GSI を認可に使わない。D4 と同じ)。一覧に出すのは通信機アカウントと組織名で、製造番号と現場名は出さない。
- 製造番号: everyone でも、初回は通信機アカウント・製造番号・暗証番号の 3 つを入れる (旧と同じ)。成功したら本人の控え (D13) にだけ残す。
- 総当たり: everyone では、割り当ての無い利用者も暗証番号を試せる (判断 9 の根拠「総当たりも割り当てられた利用者からに限られる」が弱まる)。通信機アカウントごとの失敗回数 (D5) に加え、利用者ごとの失敗回数を足す。すべての通信機を合わせて数え、60 分に 10 回失敗したら 60 分止める (429 `USER_PIN_LOCKED`)。1 人が多くの通信機を順に試すのを抑える。止めたことと試した通信機は監査に残る。疑わしい通信機は assigned に切り替える。
- 引き渡し (D4 の手順): 前のお客様の利用者も台帳の有効な利用者のままなので、新しい利用期間を everyone で始めると、新しい暗証番号が効くまでの間、前の暗証番号で入れてしまう (D4 の手順 3 の「割り当ての条件があるので入れない」が everyone では成り立たない)。新しい暗証番号が効く (通信機が新しい設定を報告する) までは新しい利用期間を assigned で始め、効いたことを確かめてから everyone にする。
- everyone の P では、最新値の可否 (運用中か) を割り当ての無い人にも答える (一覧に出ている通信機のため)。
- admin も、everyone の通信機では割り当て無しで通信機ログインに進める (実装計画の判断 9「admin も自分を割り当ててから」は assigned の通信機のこと)。

将来 (機器単位の接続):
- 通信機ログインが無いので (3) を通せない。その種類の利用期間は assigned を必須にし (everyone を選べない)、サービスの API は (1)(2)(4) で通す形が候補。everyone のままでは、サインインした人なら誰でもデータを見られるため。
- 利用期間に接続の種類を持たせるか、通信機アカウントの種類から決めるか、(3) の代わりに何を置くかは、そのチケットで決める。
- 割り当て (人 | グループ) はこのときの門になる。D13 はその前提として今入れる。

理由:
- 判断 9 の A のままでは、admin が割り当てを作るまでお客様が使い始められない。旧は暗証番号だけで入れた。everyone を既定にすると、旧と同じく暗証番号を門にして使い始められ、割り当ては要るときだけ作ればよい (ユーザー決定)。
- ログイン記録に根拠を持たせて (3) で比べると、access の切り替え・割り当ての追加・所属の変更のどれでも、記録を探して消さずに正しく落ちる。照合を使い回さない ID (世代) で行うので、同じ秒に外して付け直しても前の記録は通らない (時刻で比べると、同じ秒の再付与で前の記録が通ってしまう)。
- 利用者ごとの失敗回数は、everyone で広がった「試せる人」を、人の側から抑える。通信機ごとの回数だけでは、多くの通信機を順に試すのを止められない。

影響:
- 判断 9 を一部改める (判断 18)。assigned の利用期間では判断 9 のまま。
- 実装 : 利用期間に access・access の世代・変えた時刻と人、稼働中の指しに access と変えた時刻と人の写し。開始で access を受け (既定 everyone)、変更の API (どちらも書き込みのトランザクションに呼び出し元の検査)。shared の access の (2)(3) (根拠の ID で照合)。base の通信機の一覧 (`/me/devices`。base に GSI1 の読み取りの権限を足す)、ログイン記録の根拠 (種類・ID・世代) と版を条件にした置き換え、製造番号の控え、利用者ごとの失敗回数。監査 `dperiod.access`。
- 運用: 利用期間を始めるときに access を選ぶ (既定 everyone)。引き渡しは上の「引き渡し」のとおり、新しい暗証番号が効くまで assigned。本番の移行では、通信機ごとに access を決める (既定 everyone)。
- 利用者: 動線は変わらない。通信機ログインの一覧に、割り当てられた通信機に加えて everyone の通信機が出る。everyone の通信機では、初回に製造番号も入れる。

### 判断 1. アカウント単位で今出すもの

- 決定: A。パスキーの管理 (複数のパスキーの一覧・追加・削除)、自分に割り当てられた通信機アカウントと許可されたサービスの一覧。admin には加えて、利用者の管理・通信機の割り当て・サービスの許可・TOTP の登録。
- 初版の選択肢: A (上記)、B (パスキーの管理と admin の管理機能だけ。一覧は出さない)、C (A に加えて、組織単位の機能。判断 2 で顧客側の管理者を置く場合)。推奨は A。
- 根拠: アカウント単位で出すサービスはまだ無い。利用者が「どの通信機を扱えて、何が許可されているか」を自分で確かめられれば、admin への問い合わせが減る。一覧は台帳を読むだけで作れる。

### 判断 2. 許可を出すのは弊社 admin だけか

- 決定: A。基盤の admin だけ。台帳の割り当てに「役割」の列を持ち、後で組織の管理者を足せる形にする。
- 初版の選択肢: A (上記)、B (顧客側の管理者を置き、自組織の利用者の招待と通信機の割り当てを任せる。サービスの許可は弊社 admin のまま)、C (顧客側の管理者にサービスの許可まで任せる)。推奨は A。
- 根拠: サービスの許可は請求の実績に直結するので、弊社が握る。B は組織の境界を台帳に足し、認可の確認も増える。お客様の数が少ないうちは admin の手作業で回る。役割の列を先に持てば、B は移行なしで足せる。
- 決めていないこと: B を入れる目安 (顧客モニターの人数など)。入れるときに別に決める。

### 判断 3. サービス SPA を統合するか、別ビルドにするか

- 決定: サービス SPA は別ビルドでも配置できる。同じユーザープール、アプリクライアント、origin を用いる (D6)。
- 根拠: 既存サービスの UI と共通基盤を独立して更新しながら、サインインの状態を共有できる。

### 判断 4. RP ID を親ドメインにできるか

- 決定: A。RP ID は各環境のドメイン名そのもの (service-platform.example-cloud.com / service-platform-dev.example-cloud.com)。親ドメインにしない。dev と本番でパスキーは別に登録する。
- 初版の選択肢: A (上記)、B (親ドメイン example-cloud.com)。推奨は A。
- 根拠: 環境ごとの FQDN に RP ID を限定し、サイト間の信頼範囲を広げない。

### 判断 5. admin が利用者のパスキーを消す手段

- 決定: A。admin が他人のパスキーを消す API は無いので、本人がアカウントの画面で消す (D8 手順 1)。盗難・本人がサインインできないときは、無効化 → 全セッション失効 → 削除 → 再招待 (user_id は保つ。D8 手順 2)。受信箱の乗っ取りは D8 手順 4 (別経路の本人確認と受信箱の安全確認を先に行い、その連絡先は招待のときに台帳に控える)。
- 初版の選択肢: A (上記)、B (全セッションの失効と無効化だけにし、再招待はしない)。推奨は A。
- 根拠: 削除は本人のアクセストークンで行う DeleteWebAuthnCredential だけ (調査ノート Q3)。無効化だけではパスキーが残り、有効に戻すと同じパスキーがまた使える (推論)。消すには利用者ごと削除するしかなく、そのとき sub が変わる。user_id を挟んでいる (D3) ので、再招待しても割り当てと履歴は残る。

### 判断 6. 招待と回復の手段

- 決定: B。お客様はパスワード無しで作成し、初回と回復はメールのコード (EMAIL_OTP)、常用はパスキー。admin はパスワード + TOTP。初版より前の決定「パスワードは招待と回復のために残す」は、お客様についてはこの判断で替わった。
- 初版の選択肢: A (一時パスワードで招待し、初回に本パスワードを決め、パスキーを登録する。パスワードは残る)、B (上記)。推奨は B。
- 根拠: PASSWORD はプールの設定から外せず、パスワードを持つ利用者のパスワード サインインは止められない。パスワードは一度持たせると後から消せない。A では「招待と回復だけ」が画面の上の約束にとどまる。B から A へは後でパスワードを足せる (推論)。
- 注意 (初版のまま): 受信箱が回復の要になる。メールのコードは SES の送信に頼る (届くまでの時間、迷惑メールの振り分け)。MFA を設定した利用者はメールのコードを使えないので、お客様には TOTP を出さない。
- 採用の後のレビューで分かったこと: 案 B でも、本人はサインインした後に ChangePassword でパスワードを足せる (公式)。「作成のときに持たない」は保てるが、「パスワードの入口が無い」は保証できない。扱いは D1 の「パスワードの後付け」。PoC の後は web ACL で止める (判断 15)。

### 判断 7. トークンの有効期間と保存場所

- 決定: T2。ID / アクセス 60 分、更新 24 時間、localStorage。
- 初版の選択肢: T1 (60 分 / 更新 30 日 / localStorage)、T2 (上記)、T3 (60 分 / 更新 12 時間 / sessionStorage)。推奨は T2。
- 根拠: パスキーなら 1 日 1 回のサインインは重くない。保存場所を変えても XSS の被害は変わらない (CSP は軽減策で、保証ではない)。sessionStorage は新しいタブで切れ、別ビルドを新しいタブで開くと入り直しになる。利用停止は台帳で即時に効かせる。
- 注意 (初版のまま): 更新の期限が過ぎても、localStorage の保存データは自動では消えない。共用の端末ではサインアウトを案内する (D1)。
- PoC の後: 更新トークンの rotation を足した (判断 14)。この決定 (60 分 / 24 時間 / localStorage) は変えない。

### 判断 8. admin に TOTP を求めるか

- 決定: A。admin は TOTP 必須。admin を有効にするのは、別の admin が別経路で本人を確かめた後 (D9)。「パスキー以外の強化 (TOTP 必須化) は後回し」はお客様の TOTP のことと読み、admin には当てはめない。
- 初版の選択肢: A (上記)、B (TOTP を持ち込まない。admin も JWT と admin グループと WAF だけで守る)、C (admin の条件をパスキーにする)。推奨は A。
- 根拠: B では、admin のパスワードかメールの受信箱を取られると、そのまま admin の操作ができる。C は、サインインさえできれば誰でもパスキーを足せるので、弱い入口が残る限り強くならない (D9)。A は Cognito がパスワード サインインのたびに TOTP を求め、サーバも設定とセッションを確かめられる。

### 判断 9. 通信機の割り当てを許可の条件にするか

- 決定: A。admin が利用者を通信機の利用期間に割り当て (有効期間つき)、通信機ログインは「割り当て + 暗証番号」を条件にする (D4)。
- 初版の選択肢: A (上記)、B (旧と同じく暗証番号だけを条件にし、割り当ては表示と実績のためだけに持つ)。推奨は A。
- 根拠: 暗証番号は 4 桁で、現場で共有されることもある。A なら「誰がどの通信機を扱えるか」が台帳で決まり、請求の実績を利用者と通信機で残せる。総当たりも割り当てられた利用者からに限られる。旧の懸念  も閉じる。
- 注意 (初版のまま): お客様が自分で通信機を足すことはできない。使い始める前に admin の割り当てが要る。
- 改め (2026-11-05、判断 18): 割り当てを条件にするのは、access が assigned の通信機の利用期間だけにした。既定の everyone では、割り当ての無い有効な利用者も暗証番号で入れる。上の根拠のうち「総当たりも割り当てられた利用者からに限られる」は everyone では成り立たないので、利用者ごとの失敗回数を足す (D14)。

### 判断 10. 社員の自己登録を作らないか

- 決定: A。自己登録は作らない。社員も admin が招待する (D2)。親  の範囲 2 の「自己登録」は外す。
- 初版の選択肢: A (上記)、B (`@example.co.jp` のメールアドレスだけ自己登録を許す。メールの確認コード付き)。推奨は A。
- 根拠: 利用者を招待制とし、社員と顧客に同じ入口の方針を適用する。自己登録の受付を設けない。

### 判断 11. パスキーを複数登録できるか (判断のときに加わった要件)

- 決定: 1 人の利用者 (独自の user_id、Cognito の 1 利用者) がパスキーを複数登録できる。上限は 20 個 (Cognito の制限)。本文は D1 の「パスキーの複数登録」。
- 要件: 1人が端末ごとに複数のパスキーを登録できる。対象はサインインする利用者単位。
- 根拠: 端末ごとに 1 個を登録しておけば、1 台を失くしてももう 1 台で入れ、締め出されにくい。Cognito は 1 利用者に 20 個まで登録でき (調査ノート Q9)、本人は一覧・追加・削除を Amplify の API で行える (調査ノート Q2)。
- 注記 (PoC 12 の後): 名前は Cognito が種類の名前 (Device-bound Passkey / Roaming passkey) を自動で付け、設定できない。画面は種類の名前と登録日時を出す。

### 判断 12. admin のセッションが TOTP を通ったことの確かめ方 (D9)

- 決定: (b)。台帳の `mfa_enabled_at` とトークンの `auth_time` で作る。PoC の結果を受けた設計判断 (2026-11-02)。
- 根拠: PoC 6 で、(a) の `acr` / `amr` は未提供と分かった。`TARGET_ACR_VALUES` は無視され、どのトークンにも `acr` / `amr` が無い。
- 将来: 提供が来たら (a) を試し直す。その時の既定値は `urn:cognito:loa:4`。Amplify 6.20 は `TARGET_ACR_VALUES` を渡せないので、SDK を直接呼ぶ。

### 判断 13. admin の回復 (D8 / D9)

- 決定: admin の回復で「TOTP の解除だけ」は使わない。削除と再招待 (D8 手順 2) にする。PoC の結果を受けた設計判断 (2026-11-02)。
- 根拠: PoC 11 で、TOTP を外すと、TOTP の間に登録したパスキーとメールのコードで入れると分かった。admin が他人のパスキーを一覧・削除する API は無く、AdminGetUserAuthFactors の `WEB_AUTHN` で分かるのは有無までである (D8)。
- 注記: TOTP の現在状態は AdminGetUser の UserMFASettingList で見る。AdminGetUserAuthFactors の `ConfiguredUserAuthFactors` は、TOTP を外しても `SOFTWARE_TOKEN` を残し、使えない要素も出す (PoC 5 / 11)。
- 影響: D9 の「TOTP を解除する」の操作と API、admin の状態の「停止」を外した。緊急の復旧も再招待にした。

### 判断 14. 更新トークンの rotation (判断 7 / D1)

- 決定: rotation を採る。アプリクライアントの ExplicitAuthFlows から `ALLOW_REFRESH_TOKEN_AUTH` を外し、`RetryGracePeriodSeconds` は 30 秒にする (複数のクライアントからの再試行を考慮する)。判断 7 の決定 (60 分 / 24 時間 / localStorage) は変えない。PoC の結果を受けた設計判断 (2026-11-02)。
- 根拠: PoC 10 で、Amplify 6.20 が GetTokensFromRefreshToken で更新し、古いトークンの再利用を検出すると分かった。
- 注意: PoC の rotation 有りのクライアントは `ALLOW_USER_AUTH` だけで、猶予は 0 秒だった。`ALLOW_USER_SRP_AUTH` を残した組み合わせと猶予 30 秒は、配備のときに確かめる。

### 判断 15. お客様のパスワードの後付け (D1)

- 決定: ユーザープールの web ACL で ChangePassword を Block して止める (dev と本番の両方)。規則は `x-amz-target` が `AWSCognitoIdentityProviderService.ChangePassword` の要求を Block。PoC の結果を受けた設計判断 (2026-11-02)。
- admin 自身のパスワードの変更: 別の admin が AdminSetUserPassword で一時パスワードを出し、本人が NEW_PASSWORD_REQUIRED で決め直す。ChangePassword を使わない。
- 根拠: PoC 14 で、SDK を直接呼べば後付けできると分かった。web ACL で 403 になり、admin の招待・TOTP の登録・AdminSetUserPassword は止まらない。
- 注意: PoC で一時パスワード → 本パスワードを試したのは、TOTP の無い admin 役である。TOTP を持ったままの admin での流れ (TOTP がいつ求められるか) は、実装のときに確かめる。

### 判断 16. 再招待の古い sub (D3 / D12)

- 決定: 再招待で古い sub の行を消さず、無効の印を付けて残す。CloudTrail の `additionalEventData.sub` から後で user_id を引くため。PoC の結果を受けた設計判断 (2026-11-02)。
- 根拠: PoC 13 で、パスキーの登録・削除とパスワードの後付けは、アカウントの CloudTrail に sub 付きで残ると分かった。
- 影響: 追う手段は CloudTrail にする (D12)。API の引き当ては、無効の印の付いた行を「引けない」として扱う (D3、D9)。

### 判断 17. 割り当ての相手にグループを足すか (2026-11-05)

- 決定: 足す。割り当ての相手は人かグループ (D13)。木は 3 段まで、段の名前は自由、人は複数のグループに属せる。所属の行に経路を写す。設計判断 (2026-11-05)。
- 選択肢: A (人だけ。今のまま)、B (人 | グループ)、C (グループだけ。1 人に渡すときも 1 人のグループを作る)。推奨は B。
- 根拠: A は会社や部署の人数分の割り当てを通信機ごとに作ることになり、人の出入りのたびに全部の通信機を直す。C は既存の人宛の割り当てを作り直すことになり、1 人だけに渡したい通信機にもグループの手間が出る。B は既存の割り当てをそのまま生かし、組織の形で渡したいときだけグループを使える。
- 段の名前: 固定しない (設計判断)。会社・部署・課のほか、県・事務所・出張所、コンサル・支店の形がある。段の名前の列を持たないので、判定は名前に依らない。
- 影響: D13。admin の操作にグループの管理が加わる。
- 将来: 判断 2 の B (組織の管理者) を入れるときは、グループごとに管理者を置き、その下の段の所属と割り当てを任せる形が候補になる。グループの付け替え (親の変更) が要るなら、所属の経路の書き換えを含めて別に設計する。

### 判断 18. 割り当ての無い人も通信機ログインに進めるか (everyone) (2026-11-05)

- 決定: 通信機の利用期間に access (everyone / assigned) を持ち、既定を everyone にする。everyone は「サインインした人なら誰でも」。判断 9 は assigned の利用期間だけに残す (D14)。設計判断 (2026-11-05)。
- 選択肢: assigned と everyone を利用期間ごとに選ぶ。
- 根拠: 明示的な割り当てを求める方式と、サインインと通信機の秘密で利用を開始する方式を使い分ける。どちらも有効な利用期間とサービス許可を確認する。
- 影響: 一覧に、ほかのお客様の通信機アカウントと組織名が出る。割り当ての無い人も暗証番号を試せるので、利用者ごとの失敗回数を足す。引き渡しでは、新しい暗証番号が効くまで新しい利用期間を assigned にする (D14)。
- 将来: 機器単位の接続 (通信機ログインが無い) では assigned を必須にし、割り当て (人 | グループ) が門になる (D14 の「将来」)。

### 判断 19. グループと access を入れる時期 (2026-11-05)

- 決定: グループと access を利用者データの移行前に組み込む。
- 根拠: 後から入れると、人単位で写した割り当てをグループに作り直すことになる。access の属性が無い利用期間は everyone と読むので、先に入れても既存の行を書き換えなくてよい。
- 影響: 本番の移行の手順 (RUNBOOK) に、グループを先に作ることと、通信機ごとの access の決めを足す 。

### 判断 20. admin にパスキーの入口を足す (2026-11-06)

- 決定: パスワード + TOTP で入った後にパスキーを登録し、通常の入口からパスキーでも入れる。入口が 2 つあっても、本人確認つきのパスキーとパスワード + TOTP はどちらも強い入口なのでよい。設計判断 (2026-11-06)。パスキーだけを admin の条件にする案は採らない。
- 事実: Cognito はプールの `WebAuthnConfiguration.FactorConfiguration=MULTI_FACTOR_WITH_USER_VERIFICATION` と利用者の `WebAuthnMfaSettings.Enabled=true` により、本人確認つきのパスキーを MFA として扱う。パスワードを選ぶと TOTP が必要なままで、パスキーを第二要素には使えない。[MFA の公式表](https://docs.aws.amazon.com/cognito/latest/developerguide/user-pool-settings-mfa.html)、[AdminSetUserMFAPreference](https://docs.aws.amazon.com/cognito-user-identity-pools/latest/APIReference/API_AdminSetUserMFAPreference.html)。
- 設計: CloudFormation は `WebAuthnFactorConfiguration` を設定する。登録完了 API は現在の TOTP を確かめ、失効・台帳更新へ進む。有効な admin がパスキーを登録した後、`POST /me/passkey-mfa` が D9 を確かめて WebAuthn MFA を有効化する。既に有効な admin は `admin_ops.py enable-passkey-mfa` を使う。準備中と確認待ちは従来の手順で有効化し、有効な admin だけ画面にパスキー管理を出す。
- セッション: `auth_time > mfa_enabled_at` と Cognito の現在の TOTP を確かめる admin_guard は維持する。登録後のパスキーによるサインインも受け付ける。admin は近道の対象外で、パスキーの登録をサインイン後に強制しない。
- dev 実測で確定した前提: パスキー未登録の利用者に WebAuthn MFA を有効化すると、本人 API と IAM の API はともに InvalidParameterException で拒否した。理由は適用可能な WebAuthn 資格情報が無いこと。初回の TOTP 登録時には有効化できないため、パスキー登録 → 有効化の順にする。画面は設定成功後に登録完了を知らせ、設定だけ失敗した場合は再登録せず再試行できる。追加直後の利用設定が失敗したときは sessionStorage に印を残す。次に画面を開いたとき、印がある場合だけ 1 回再試行し、成功で印を消す。失敗なら印と再試行ボタンを残す。409 PASSKEY_REQUIRED は「先にパスキーを登録してください」と案内する。
- 監査: `POST /me/passkey-mfa` は D9 を通す本人だけを対象にし、`admin.passkey_mfa_requested` を書けた後に Cognito を更新する。Cognito の結果を `admin.passkey_mfa_enabled` (result=ok / failed、失敗時の理由コード) として最善努力で追記し、追記失敗で業務を止めない。パスキーが無ければ 409 PASSKEY_REQUIRED、それ以外の失敗は 503。台帳の状態と登録時刻は変えない。CLI は登録済みのパスキーを先に確かめ、要求の前と成功の後を `script.enable_passkey_mfa` の step=requested / enabled で記録する。登録操作そのものは引き続き Cognito の CloudTrail で追う。
- 配備: 更新前に変更セットで SignInUserPool の Modify / Replacement=False を確かめる。プールを作り直さない。
- E2E: dev の仮想認証器で登録・パスキー認証・管理 API 200 を確認した。候補は `PASSWORD / PASSWORD_SRP / WEB_AUTHN` で `EMAIL_OTP` は無い。削除後のパスワード + TOTP も通る (PoC 15)。

| 利用をやめる | admin が台帳で停止し、Cognito で無効化。サービスの許可を終える。記録は残す |
| admin が TOTP を失くした | 別の admin が再招待する (D8 手順 2。TOTP の解除だけは使わない。判断 13)。一時パスワードは別経路で渡す → 本人が本パスワードと TOTP を登録 (確認待ち) → 別の admin が別経路で確かめて、台帳と admin の状態を有効に戻す (それまで admin の操作は 403)。使える admin がいなければ D9 の緊急の復旧 |
| admin がパスワードを変える | 別の admin が AdminSetUserPassword (`Permanent=false`) で一時パスワードを出し、社内の別経路で渡す → 本人が NEW_PASSWORD_REQUIRED で決め直す (判断 15) |
| グループを作る・人を属させる | admin がグループの木 (3 段まで。段の名前は自由) を作り、人を属させ、通信機の利用期間を人かグループに割り当てる (D13)。組み替えは新しいグループを作って移し、古いグループを終える |
| 通信機を割り当てた人だけにする | admin が通信機の利用期間の access を assigned にする。割り当ての無い人とその記録は次の要求から通らない (D14)。引き渡しの直後も、新しい暗証番号が効くまで assigned にする |

### 利用者への影響

- 旧のサイトから新しいサイト (service-platform.example-cloud.com) に移る。専用の認証基盤を使う。
- 初回はメールのコードで入り、パスキーを登録する。端末ごと (PC とスマホなど) に登録しておくと、1 台を失くしてももう 1 台で入れる。以後はメールアドレスの入力とパスキーで入る。
- 通信機ログインは旧と同じ 3 項目。割り当てられた通信機だけを扱える (判断 9)。D14  の後は、access が everyone (既定) の通信機はサインインした人なら誰でも一覧に出て、暗証番号で入る。割り当てられた通信機だけになるのは、access が assigned の通信機。
