# SERVICE-PLATFORM パスキー技術資料

鍵はどこで作られ、どこにあり、どう使われるのか

2026年11月6日時点

## 1. この資料について

パスキーは、本人の端末にある鍵を使ってサインインする仕組みです。顔や指紋は、その鍵を使うために端末の中で確かめます。

この資料では、最初のメールの確認から、鍵の作成、次回のサインインまでを順に追います。構成図は実際の役割を、イラストは鍵と南京錠の例えを示します。

| 答える問い | 読むところ |
| --- | --- |
| 鍵はどこにあるの | 2〜6章、8章：鍵の生成・保存・使い方 |
| 指紋はサーバに送られるの | 6章、8章：端末内の本人確認 |
| スマホを替えたらどうなるの | 5.1節、9章：保存先と移行 |
| 偽サイトでも使われるの | 6.1節：サイトの範囲の確認 |
| 管理者はどう入るの | 10章：2つの入口 |

**最初に使う5つの言葉**

| 言葉 | この資料での意味 |
| --- | --- |
| パスキー | 2つの鍵の組で本人だと示す、サインインの仕組み |
| 公開鍵と秘密鍵 | サービスに預ける「南京錠」と、本人側に残す「鍵」。2章で役割を説明 |
| 認証器 | 端末の鍵置き場。本人の承認を受けて鍵を使う仕組み |
| 本人確認 | メールや端末の機能で、操作している本人を確かめること |
| トークン | サインイン後に使う、期限付きの入場証のような情報 |

一般利用者は、初回にメールのコードで入り、その後にパスキーを作ります。管理者の入口は10章で説明します。

根拠：ADR-001 D1、[W3C WebAuthn「概要」](https://www.w3.org/TR/webauthn-3/#sctn-intro)。

## 2. 登場するものと2つの鍵

秘密鍵は「本人だけが使う鍵」、公開鍵は「サービスに預ける南京錠」と考えてください。2つは本人の端末側で一緒に作られます。

認証の説明：緑の秘密鍵をスマホに残し、青い南京錠で表す公開鍵をサービスに預けるイラスト。

サインインのたびに鍵そのものを渡す必要はありません。「この鍵を持っている人が応えた」と分かる印を作り、サービスが確かめます。この印を署名と呼びます。

| 登場するもの | 役割 |
| --- | --- |
| 利用者の端末 | ブラウザが画面を開く。認証器が鍵を作り、秘密鍵を保管して使う |
| 鍵の保存先と同期先 | iCloudキーチェーンやGoogleパスワードマネージャーなど。Windows HelloでそのPC内に置く選択肢もある |
| SERVICE-PLATFORMの画面 | CloudFrontが入口になり、S3から画面を配る |
| 認証基盤：Cognito | 公開鍵の預かり所。メールのコードや署名を確かめる |
| メール：SES | 招待や本人確認のコードをメールで届ける |
| 業務APIと台帳 | API GatewayとLambdaが処理を受け持つ。DynamoDBの台帳で、誰が何を使えるかを確かめる |

公開鍵だけを入手しても、本人の秘密鍵で作る署名の代わりにはできません。同期する保存先では、秘密鍵の情報を保護して本人のほかの端末でも使えるようにします。

<div class="source" markdown="1">

根拠：、ADR-001 D1・D3、[Apple「パスキーのセキュリティ」](https://support.apple.com/en-us/102195)。

</div>

## 3. フェーズ全体の流れ

初回は1から2へ進みます。次回のサインインでは、作成済みの鍵を3で使います。

認証の説明：0招待、1メールのコードで初回の認証、2鍵の作成、3署名による認証、4トークンによる利用と、各段階の鍵の状態。

認証の説明：メールの確認、端末での鍵の作成、署名の確認、入場証での利用を描いた文字なしの4コマ。

<div class="source" markdown="1">

根拠：ADR-001 D1・D2。管理者の場合は10章の設計を参照。

</div>

## 4. フェーズ1：メールのコードで初回の認証

その前の「0：招待」で、管理者が利用者を用意します。管理APIがCognitoに利用者を作り、台帳にも同じ人を結び付け、操作を記録します。本人にはSESから招待メールが届きます。

本人が入口でメールアドレスを確かめると、8桁のコードがメールで届きます。開いている画面へ10分以内に入力します。これで、その受信箱を使える本人であることを確かめます。

認証の説明：ブラウザからCognitoへメールアドレスを渡し、SESから受信箱に届いたコードを入力する構成図。

認証の説明：届いたメールを見てパソコンへコードを入力する人。鍵はまだ無い。

<div class="key-state">保存されているもの：Cognitoには利用者とメールアドレス。台帳には利用者のIDと状態。秘密鍵・公開鍵は、まだありません。</div>

招待は標準ブラウザで開き、コードの入力画面を閉じずにメールを見ます。再送したら最新のコードを使います。管理者は10章の別の入口を使います。

ひとことで言うと：最初はメールを受け取れることを確かめ、鍵を作る準備をします。

<div class="source" markdown="1">

根拠：ADR-001 D1〜D3・D12、SECURITY-DESIGN「認証の境界と流れ」「監査と保持」、LoginView.vue・auth.ts。

</div>

## 5. フェーズ2：パスキーを作る

メールのコードで入った後、アカウントの画面でパスキーを追加します。鍵が無い人には、先にこの画面で登録を案内します。

1. 認証器が鍵のペアを作り、秘密鍵をそこに残します。
2. 公開鍵などの登録情報をブラウザ経由で送ります。
3. Cognitoが公開鍵を保存し、本人のアカウントに結び付けます。

認証の説明：端末の認証器で2つの鍵を生成し、秘密鍵は残し、公開鍵だけをブラウザ経由でCognitoへ登録する構成図。

認証の説明：スマホの中で緑の鍵が生まれ、青い南京錠だけを建物へ直接届けるイラスト。

<div class="key-state">作る場所：本人側の認証器。保存先：秘密鍵は本人側、公開鍵はCognito。SERVICE-PLATFORMの台帳には、どちらの鍵も置きません。</div>

同期する保存先なら、秘密鍵の情報を保護して、同じアカウントのほかの端末にも届けます。これはCognitoへの登録とは別の動きです。

ひとことで言うと：本人側で鍵のペアを作り、サービスには確かめる側だけを預けます。

<div class="source" markdown="1">

根拠：ADR-001 D1、passkeys.ts、[W3C WebAuthn「登録」](https://www.w3.org/TR/webauthn-3/#sctn-registering-a-new-credential)、[Apple「同期の安全性」](https://support.apple.com/en-us/102195)。

</div>

## 5.1 どの鍵置き場に保存するか

使っているブラウザ名だけでは保存先は決まりません。作成時に、保存先の名前を確かめます。

| 選んだ保存先 | 鍵の保存と、端末を替えるとき |
| --- | --- |
| Windows Helloの「このWindowsデバイス」 | そのPC内（ローカル）に保存。ほかのPCには同期されず、別に登録する |
| iCloudキーチェーン | 同じApple Accountの対応端末へ保護して同期。同じアカウントで復旧の条件を満たせば使える |
| Googleパスワードマネージャー | 同じGoogleアカウントの対応するChrome・Androidへ同期。新端末では必要なロック解除を行う |
| EdgeのMicrosoftパスワードマネージャー | 個人のMicrosoftアカウントで使う、WindowsのEdgeの保存先。同じアカウントへ保護して同期し、新端末では保存先のPINで確認する |

Windows Helloで顔や指紋を確かめる画面が出ても、そのPCだけに保存したとは限りません。本人確認の方法と保存先は、分けて見ます。対応状況はOSやブラウザによって変わります。

**場面B：PCからQRでスマホに作る**

PCで登録を始め、別の端末へ保存する選択肢を選びます。PCに出たQRを近くのスマホで読み、スマホで承認します。鍵が生まれるのはスマホ側です。PCには、その秘密鍵を保存しません。両方のBluetoothとインターネット接続が必要です。作成済みの鍵を使う「場面D」とは目的が違います。

利用できる保存先と端末の組み合わせは、OS・ブラウザ・認証器の案内で確認します。

<div class="source" markdown="1">

根拠：ADR-001 D1、[Microsoft「作成と保存」](https://support.microsoft.com/en-us/accounts-billing/security/create-save-passkey)、[Microsoft Learn「Windowsのパスキー」](https://learn.microsoft.com/en-us/windows/security/identity-protection/passkeys/)、[Apple「保存と同期」](https://support.apple.com/en-us/102195)、[Google「Chromeでの管理」](https://support.google.com/chrome/answer/13168025?hl=ja&amp;co=GENIE.Platform%3DDesktop)、[Microsoft Edge公式ブログ](https://blogs.windows.com/msedgedev/2025/11/03/microsoft-edge-introduces-passkey-saving-and-syncing-with-microsoft-password-manager/)。

</div>

## 6. フェーズ3：パスキーでサインインする

次回は通常の入口でメールアドレスを入力し、パスキーを使います。

1. Cognitoが「今回だけの問い」を送ります。この問いをチャレンジと呼びます。
2. ブラウザが、開いているサイトでそのパスキーを使ってよいか確かめます。
3. 端末で、顔・指紋・PINのいずれかを使って本人を確かめます。
4. 認証器が秘密鍵を使い、今回の問いに対応する署名を作ります。
5. Cognitoが、預かっている公開鍵で署名を確かめます。
6. 確認が通ると、サインイン後に使うトークンを発行します。

認証の説明：Cognitoからの今回の問いに対し、端末内で本人を確認して秘密鍵で署名し、公開鍵で検証する構成図。

認証の説明：問いを受けたスマホが顔で確認し、緑の鍵で紺の印を作り、建物が青い南京錠で照合するイラスト。

<div class="key-state">使うもの：端末側の秘密鍵と、Cognitoの公開鍵。サインインで送るのは署名した応答です。秘密鍵そのものも、顔・指紋のデータも送信しません。</div>

ひとことで言うと：本人の鍵で今回だけの印を作り、サービスが預かった南京錠で確かめます。

<div class="source" markdown="1">

根拠：、auth.ts、[W3C WebAuthn「認証」](https://www.w3.org/TR/webauthn-3/#sctn-verifying-assertion)・[「端末内の生体認証」](https://www.w3.org/TR/webauthn-3/#sctn-authenticator-local-biometric)。

</div>

## 6.1 偽サイトと、別の端末からの利用

**偽サイトで本物用の鍵を使えない理由**

パスキーには、使えるサイトの範囲があります。この範囲をRP IDと呼びます。ブラウザが範囲を確かめるため、見た目をまねた別ドメインの偽サイトでは、本物用のパスキーを自由に使えません。SERVICE-PLATFORMは環境ごとのサイトのドメイン名を範囲にしています。開発環境と本番環境の鍵は別です。

認証の説明：本物のサイトとの接続を認め、別ドメインの偽サイトからの接続を止めるイラスト。

**場面D：PCでスマホのパスキーを使う**

PCに出たQRを近くのスマホで読み、スマホで本人確認をします。署名を作るのはスマホです。署名の応答を受けてPC側でサインインが終わり、秘密鍵をPCへコピーしません。両方のBluetoothとインターネット接続が必要です。Bluetoothが無い、または利用を止めているPCでは、このQR方式を使えません。

認証の説明：近くのスマホでPCのQRを読み、スマホに鍵を残してPCでサインインするイラスト。

受信箱や端末のロックは引き続き守ります。メールのコードも入口になるため、受信箱を他人に使われないことが大切です。保存先と使い方は5.1節を参照してください。

<div class="source" markdown="1">

根拠：ADR-001 D1・D7、[W3C WebAuthn「RP ID」](https://www.w3.org/TR/webauthn-3/#sctn-rp-id)、[FIDO Alliance「別端末での認証」](https://fidoalliance.org/passkeys/)、[Apple「別端末での利用」](https://support.apple.com/guide/iphone/iphf538ea8d0/ios)。

</div>

## 7. フェーズ4：サインイン後は入場証で使う

サインイン後は、ブラウザに保存したトークンを業務APIに提示します。この利用では、パスキーの鍵で毎回署名しません。画面はCloudFront経由でS3から受け取り、業務の要求は台帳の確認へ進みます。

認証の説明：CloudFrontから画面のS3と業務APIへ進み、LambdaがDynamoDBの台帳と監査を使う全体構成図。

入場証があっても、何でも使えるわけではありません。APIは台帳で、現在の利用者の状態、利用期間や許可を確かめます。台帳の停止は、発行済みの入場証が期限内でも業務APIに効きます。本人の状態確認など、限られた例外は残ります。

ID・アクセストークンの期限は60分です。更新用の入場証は最初のサインインから24時間で、更新してもこの期限は延びません。

<div class="source" markdown="1">

根拠：ADR-001 D1・D3・D9、SECURITY-DESIGN「トークンとブラウザ」「台帳による利用者の確定と停止」。

</div>

## 8. 鍵の居場所のまとめ

端末の鍵置き場と、ブラウザの保存領域は別です。サインイン用の秘密鍵は前者、サインイン後の入場証は後者にあります。

| 情報 | 端末 | 同期の雲 | Cognito | SERVICE-PLATFORMの台帳 |
| --- | --- | --- | --- | --- |
| 秘密鍵 | 認証器が保管し、署名に使う | 対応する保存先だけ、保護して同期 | 渡さない | 置かない |
| 公開鍵 | 認証器が作り、登録時に渡す | 保存先の仕組みによる | 本人の登録に結び付けて保存し、検証に使う | 置かない |
| 指紋・顔の照合用データ | 端末内で本人確認に使う | パスキーの同期対象ではない | 渡さない | 置かない |
| トークン | ブラウザの保存領域に置き、利用時に送る | SERVICE-PLATFORMは同期しない | 発行元 | 入場証そのものは置かない |

トークンの保存領域はlocalStorageという、同じサイトの画面が使えるブラウザ内の置き場です。ブラウザを閉じるだけではサインアウトになりません。共用PCなどでは、使い終えたらサインアウトします。

**SERVICE-PLATFORMが受け取らないもの**

秘密鍵そのものと、顔・指紋の照合用データは受け取りません。一般利用者にはSERVICE-PLATFORM用のパスワードを作りません。管理者だけは、Cognitoでパスワードを扱う入口も持ちます。

公開鍵は秘密ではありません。それでも、誰の登録かを正しく結び付けて守ります。公開鍵と、業務で誰が何を使えるかという台帳の情報は、役割が違います。

ひとことで言うと：本人側に鍵、認証基盤に確かめる情報、業務側に利用の許可があります。

<div class="source" markdown="1">

根拠：ADR-001 D1・D3、SECURITY-DESIGN「トークンとブラウザ」、[W3C WebAuthn「端末内の生体認証」](https://www.w3.org/TR/webauthn-3/#sctn-authenticator-local-biometric)、[Apple「保存と同期」](https://support.apple.com/en-us/102195)。

</div>

## 9. 端末を替える・失くす・複数持つ

新しい端末へ替える前に、使える入口を残しておきます。移行先でサインインできることを確かめてから、古い端末を手放します。

認証の説明：保護された同期を通じて古いスマホと新しいスマホで同じパスキーを使うイラスト。

| 場面 | 進め方 |
| --- | --- |
| 同期する保存先で機種変更 | 同じアカウントで同期・復旧し、新端末で使えることを確認する |
| その端末だけに保存していた | 別のパスキーやメールのコードで入り、新端末に登録する。管理者は10章の入口を使う |
| 保存先のサービスが変わる | 自動移行を前提にせず、新しい保存先で別に作り、確認する |
| PCとスマホを両方使いたい | それぞれに1つずつ登録しておくと、一方が使えなくても残りで入れる（1人20個まで） |
| 古い登録を消したい | 本人がアカウントの画面で、種類名・登録日時・認証器の種類を確かめて削除する |
| 盗難や乗っ取りの疑い | 管理者へ連絡する。停止と、本人を確かめたうえでの再招待を行う |

2台に別々の鍵を登録することと、同じ鍵を同期して2台で使うことは別です。同じ登録をSERVICE-PLATFORMから削除すると、その登録で入っていた各端末からも新しくサインインできなくなります。

パスキーの削除だけでは、サインイン済みの状態は一括で終わりません。逆に、サインイン済みの状態を失効させるだけでは、パスキーは消えません。受信箱も使えない場合は、管理者が別の経路で本人と受信箱の安全を確かめます。

<div class="source" markdown="1">

根拠：ADR-001 D1・D8・判断11、PasskeyManager.vue・passkeys.ts、[Apple「保存と同期」](https://support.apple.com/en-us/102195)、[FIDO Alliance「端末の変更」](https://fidoalliance.org/passkeys/)。

</div>

## 10. 管理者には2つの入口を用意する

管理者の二つの入口は ADR-001 判断20 に基づき実装しています。

管理者は、最初にパスワードと認証アプリで入る準備をします。本人以外が登録を確かめ、有効にしてから使います。入った後は、アカウントの画面でパスキーを追加できます。

認証の説明：最初にパスワードと認証アプリを設定し、有効化後にパスキーを登録すると、以後2つの入口を選べる設計図。

| 入口 | 入り方 |
| --- | --- |
| A：管理者用の入口 | パスワードを入力し、認証アプリの一時的なコードを入力する |
| B：通常の入口 | 登録済みのパスキーを使い、端末で顔・指紋・PINによる本人確認を行う |

認証アプリの方式をTOTPと呼びます。入口Bでは、鍵を持つことと端末内の本人確認を組み合わせます。どちらも強い入口として扱う設計です。メールのコードでは入れません。

パスキーを登録しても、認証アプリの設定と本人以外による有効化は維持します。パスキーだけを用意した管理者は作りません。管理者として何ができるかは、入口とは別に台帳などで確かめます。

ひとことで言うと：最初はパスワードと認証アプリで準備し、その後はパスキーの入口も選べます。

<div class="source" markdown="1">

## 11. 守りの要点

鍵だけでなく、メールの受信箱、端末のロック、サインイン済みの画面も守ります。

| 守り | 何を確かめる・制限するか |
| --- | --- |
| サイトの範囲：RP ID | 環境ごとのサイトに結び付け、別の範囲から本物用の鍵を使わせない |
| 端末での本人確認 | SERVICE-PLATFORMでは必須。顔・指紋・PINなどで、本人が鍵を使うことを端末で確かめる |
| 今回だけの問い | 今回に対応する署名を求め、過去の応答の使い回しを防ぐ |
| メールのコード | 8桁、10分以内。再送時は最新のものを使う。コードのメールにはリンクを入れない |
| 入場証の期限 | ID・アクセスは60分。更新は最初のサインインから24時間。更新しても最終期限を延ばさない |
| 台帳での停止 | 期限内の入場証でも、停止された利用者の業務利用を拒む。状態確認などの限定的な例外がある |
| 管理者の入口 | 認証アプリの設定と本人以外の有効化を維持し、管理者の現在の状態も確認する。パスキー登録後も二つの入口を維持 |
| 監査 | 招待・停止などの操作を記録。本人が直接行うパスキーの登録・削除は、CloudTrailというAWSの記録で追う |

画面の入口とCognitoには、それぞれWAFという保護の仕組みがあります。ここで行う要求数の確認と、端末での本人確認は別の守りです。

WAF と API のスロットリングで要求数を制御し、端末内の本人確認と組み合わせます。

サインイン後の入場証を盗まれる危険は残ります。受信箱や端末を安全に保ち、共用PCでは使い終えたらサインアウトします。監査の台帳だけに、すべての拒否や認証操作が残るわけではありません。

<div class="source" markdown="1">

根拠：ADR-001 D1・D3・D7・D9・D12、SECURITY-DESIGN「WAF・直叩き・スロットリング」「監査と保持」「認証の境界と流れ」、infra/core/template.yaml。管理者の入口は ADR-001 判断20。

</div>

## 12. 用語集と参照資料

最初の5語に加え、図や本文を読むときに使う言葉です。

| 用語 | 意味 |
| --- | --- |
| WebAuthn | ブラウザと鍵置き場が協力して、鍵の作成・登録・利用を行う共通の仕組み |
| RP ID | パスキーが使えるサイトの範囲。SERVICE-PLATFORMでは環境ごとのサイトのドメイン名 |
| チャレンジ | サインインのたびにサービスから届く、今回だけの問い |
| 署名 | 秘密鍵で作る確認用の印。対応する公開鍵で正しいか確かめられる |
| Cognito | メールのコードやパスキーを確かめる認証基盤 |
| SES | 招待やコードのメールを届ける仕組み |
| CloudFront | 画面と業務APIへの入口。画面そのものはS3から配る |
| 同期型／端末固定型 | 本人の対応端末へ保護して共有する保存先／その端末内だけで使う保存先 |
| TOTP | 認証アプリが時刻に基づいて作る、一時的な確認コードの方式 |
| 利用期間 | 通信機やサービスを使う期間。鍵や入場証の有効期限とは別 |
